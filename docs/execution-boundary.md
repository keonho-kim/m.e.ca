# 호스트 실행과 승인 경계

[현재 실행 구조](runtime.md) · [도구 목록](tools.md) · [설정](configuration.md) · [플랫폼 검증](development.md#플랫폼-실행-검증)

이 실행 경계는 tui·full의 TUI·CLI와 모든 Provider에 공통이다. full의 서버·WebUI도 같은 도구 정책을 사용한다. 서버 토큰 인증·TLS·Origin 검사는 API 접근을 통제하며 호스트 도구의 파일·명령 권한을 격리하지 않는다. 자체 서버 API는 task ID에 연결한 일회성 승인 요청과 결정 채널을 제공한다. [서버 인증과 작업 제어](server.md)를 함께 따른다.

MECA는 설치된 호스트 셸과 개발 도구를 실행 사용자 권한으로 사용한다. 프로젝트 경로는 기본 작업 위치이며 OS 보안 경계가 아니다. 승인 대상 작업은 기본 모드에서 사용자 승인을 받고 All Mighty에서 자동 승인한다.

모델은 `codemode`에서 JS·TS로 도구를 호출한다. 코드 자체는 승인 대상이 아니며, 실제 이름과 인자가 확정된 내부 호출마다 아래 정책을 적용한다. 셸 AST 분석은 `tools.execute_command`에 전달된 완성된 명령을 검사한다. 코드 실행기의 직접 I/O 제한·자원 예산·중단 계약은 [Code Mode](codemode.md)를 따른다.

## 셸과 개발 환경

- execute_command는 /bin/sh -c로 실행하며 매 호출을 현재 세션의 정규화한 프로젝트 디렉터리에서 시작한다. cd는 해당 호출에만 적용된다.
- HOME·PATH·TMPDIR·개발 설정·프록시·인증 에이전트 등 부모 프로세스 환경을 그대로 전달한다. 셸 별칭·함수·대화형 초기화 파일을 재현하는 계약은 아니다.
- DNS 설정과 마운트·네트워크·사용자 캐시를 호스트 상태 그대로 사용한다. 언어별 실행기나 캐시 경로 예외를 만들지 않는다.
- 파일 접근·삭제·하드링크·소켓은 OS 사용자 권한을 따른다. 프로젝트 밖 경로도 명령과 자식 프로그램이 접근할 수 있다.
- MECA는 명령 전에 프로젝트나 캐시 전체를 순회하지 않는다.

명령 문자열 검사와 사용자 승인은 자식 프로그램 전체에 대한 파일시스템 격리가 아니다. 빌드·테스트·패키지 설치도 호출된 코드의 부작용을 가질 수 있다. 강한 격리가 필요한 작업은 사용자가 별도로 격리한 실행 환경에서 MECA를 실행한다. MECA는 그 환경의 OS 권한을 우회하거나 승격하지 않는다.

## 자동 승인과 파일 도구

`!permission` 또는 `config.toml`의 `permission`으로 기본(`default`)과 All Mighty(`all_mighty`)를 선택한다. 기본은 승인 대상 명령·작업 디렉터리·파일 변경을 사용자에게 제시하고, 비대화형 실행에서는 승인이 필요한 작업을 중단한다. All Mighty는 외부 전송과 프로젝트 밖 삭제를 포함한 승인 대상 도구 호출을 모두 자동 승인한다. 승인 기록의 출처는 각각 `user`와 `all_mighty`다.

승인 모드는 요청을 시작할 때 고정한다. 두 모드에서 인자·자격 증명·보호 경로·대상 버전을 검사하고 준비한 실행은 한 번만 수행한다. 아래 표는 기본 모드의 판정이다.

프로젝트 루트는 현재 세션의 `project_root`다. 새 대화는 meca를 실행한 폴더 또는 `meca <path>`의 지정 폴더를 사용하고, 저장된 대화를 선택하면 그 세션의 저장된 프로젝트를 사용한다. 개별 셸 호출에서 `cd`해도 삭제·이동 정책의 기준 프로젝트는 바뀌지 않는다.

다른 위험 동작이 없는 명령을 `~/workspace/meca/project` 세션에서 실행하는 예시다. 보호 경로 차단은 승인 요청보다 우선하며, Git 작업 등 별도 승인 사유는 함께 적용한다.

| 명령 | 판정 |
| --- | --- |
| `rm sample.py`, `rm -rf src` | 내부 하위 경로 삭제: 자동 승인 |
| `rm ../t2/sample.py` | 외부 경로 삭제: 승인 요청 |
| `rm -rf .`, `rm -rf ..` | 프로젝트 루트 자체·상위 경로 삭제: 차단 |
| `rm *.tmp`, `rm "$(cat target.txt)"` | 실행 전 삭제 대상을 확정할 수 없음: 승인 요청 |
| `mv a.txt b.txt`, `mv src/a.txt .` | 출발지·실제 도착지가 내부 하위 경로: 자동 승인 |
| `mv a.txt ../t2/a.txt` | 외부 경로로 이동: 승인 요청 |
| `mv . ../backup` | 프로젝트 루트 자체 이동: 차단 |
| `git rm sample.py` | 실제 Git 변경: 내부 파일이어도 승인 요청 |

전용 파일 도구는 호스트의 일반 경로를 사용할 수 있다. 상대 경로는 프로젝트를 기준으로 해석한다. 대상 정규화·symlink 해석·원본 버전·정확한 부분 수정·승인된 diff 연결은 파일 도구가 소유한다. 파일 저장은 같은 디렉터리에 만든 임시 파일을 원자적으로 교체한다. 파일·디렉터리 이동은 execute_command의 mv로 수행하며 셸 검사와 OS 권한을 따른다.

전용 파일 도구와 파일 탐색기는 MECA 상태 및 알려진 개인 비밀 경로에 대한 직접 접근을 거절한다. 프로젝트 루트나 보호 경로의 상위 디렉터리를 이동하지 않는다. 이 방어는 호스트 셸·그 자식 프로그램까지 강제하는 보안 격리가 아니다. 로그·저장·모델 문맥·표시의 자격 증명 제거도 별도로 유지한다.

## 셸 구문 분석과 사고 방지

준비 시와 실행 직전에 셸 명령을 mvdan/sh의 AST로 파싱하여 인용·이스케이프·연결·파이프·리다이렉션·중첩 실행을 구분한다. 명령 이름을 먼저 확정하고, 단일 정밀 검사 목록에 등록된 명령의 인자만 해석한다. 목록 밖 실행 파일에는 같은 기본 허용 규칙을 적용하며 그 인자·내부 실행·하위 프로세스 동작은 추적하지 않는다. 분석 중 명령·명령 치환을 실행하거나 glob을 실제 파일 목록으로 확장하지 않는다.

관리 대상은 [정밀 검사 목록](../internal/policy/command/inspection.go) 하나다. 별도 허용 목록이나 명령 종류별 예외는 두지 않는다. 목록 밖 명령에 전달된 문자열은 실행 코드로 추측하지 않는다. 반면 같은 셸이 별도 단계로 실행하는 검사 대상 명령, 실행 가능한 명령 치환·함수 본문·리다이렉션은 공통으로 검사한다. 임의 실행 파일과 그 하위 코드의 안전성을 인증하는 기능은 아니다.

| 검사 대상 | 세부 판단 |
| --- | --- |
| rm·rmdir·unlink | 내부 하위 경로 삭제 자동 승인·외부/미확정 대상 승인·보호 루트 차단 |
| mv | 출발지·실제 도착지가 내부이면 자동 승인·외부/미확정 대상 승인·보호 경로 차단 |
| cp·install·ln·mkdir·touch·truncate·tee·리다이렉션 | 실제 쓰기 대상 |
| sed·gsed | 스크립트 효과·in-place 대상·백업 파일·별도 파일 출력·명령 실행 |
| find·xargs | 조회 인자와 삭제·출력 파일·하위 명령 구분 |
| git | 하위 명령·옵션·실행 설정에 따른 파괴 작업과 원격 변경 |
| curl·wget·scp·rsync·ssh·sftp | 명시적 데이터 전송·원격 실행·불확실한 전송 설정 |
| chmod·chown·chgrp·시스템 명령 | 권한·소유자·디스크·마운트 작업 |
| 셸·env·command·eval 등 | 실제 실행 대상, 중첩 프로그램과 작업 경로 |

판단할 수 없는 대상·확장·동적 실행은 명시적으로 처리하며, 실행 전 검사 결과가 승인한 내용과 일치하는지 다시 확인한다. 상세 구문 처리는 소스의 명령 정책 모듈이 소유한다. 검사 목록 밖 프로그램의 내부 효과를 안전하다고 인증하지 않는다.

## 외부 전송 승인

사용자가 요청한 공개 URL을 읽는 데 필요한 접속은 일반 네트워크 사용에 해당한다. 전송 데이터는 작업 목적과 필요한 정보의 범위에 맞춰 제한한다. [네트워크 사용과 데이터 전송](../SYSTEM.md#네트워크-사용과-데이터-전송)

기본 모드는 AST에서 확인한 외부 데이터 전송에 대해 호출마다 사용자 승인을 요청한다. 전체 명령과 전송 사유·확인된 목적지를 제시한다. 표시용 목적지에서는 URL 사용자 정보·쿼리 값·fragment를 제외하고 명령의 자격 증명을 마스킹한다. 사용자가 거절하면 해당 복합 명령과 같은 실행 묶음을 시작하기 전에 요청을 중단한다.

All Mighty는 전송을 자동 승인한다. 비대화형 CLI와 서버에서도 같은 승인 모드를 적용한다. 실행 시점에 준비된 명령과 대상이 여전히 유효한지 확인한다.

- curl·wget의 요청 본문·파일 업로드·form·명시적 인증·커스텀 헤더·쿼리 데이터와 원격 변경 메서드를 검사한다. GET으로 바꾸거나 파이프·중첩 셸·함수·변수로 감싸도 해당 실행 노드에서 검사한다. 명시적 전송 설정 파일·미확정 인자·지원하지 않는 옵션도 검토 대상으로 둔다.
- 단순 다운로드·일반 개발 명령은 같은 기본 허용 정책을 적용하고, 문서에 인용한 명령은 실행 코드로 해석하지 않는다. 쿼리나 커스텀 헤더가 있는 다운로드는 데이터를 전송할 수 있어 승인이 필요할 수 있다. 직접 지정한 loopback HTTP API 테스트는 추가 전송 승인을 요구하지 않는다. 리다이렉트·프록시·주소 재지정이 결합되면 loopback 예외를 적용하지 않는다.
- scp·rsync는 원격 목적지로의 복사와 로컬 복사·다운로드를 구분한다. ssh·sftp의 원격 실행·세션과 Git push도 검토하며, SSH 별칭이나 Git remote 설정을 읽어 실제 접속 주소를 추측하지 않는다.

이 검사는 명령문에 드러난 전송 효과에 대한 승인 장치다. 임의 프로그램·생성 코드·의존성 내부의 통신, 암묵적 사용자 설정·프록시, URL 경로나 다른 필드에 숨긴 데이터 등 모든 유출 경로를 통제하는 네트워크 방화벽은 아니다. LLM Provider 통신과 호스트의 패키지 관리자·네트워크 기능은 유지한다.

## 브라우저 조작 승인

조작·관찰 도구는 system 범위에서 전용 세션을 사용한다. `open`으로 HTTP(S) 주소를 열거나 관찰·이어 읽기·스크롤·요소 대기·뷰포트 변경·닫기를 수행할 때는 승인 절차를 거치지 않는다.

클릭·입력·키 입력·선택·체크·체크 해제·호버·뒤로·앞으로·새로고침은 기본 모드에서 승인을 요청하고 All Mighty에서 자동 승인한다. 루프백에도 같은 기준을 적용한다. 실행 시점에 페이지 주소가 달라지면 후보를 거절한다. 시간 초과 뒤에는 페이지 상태를 관찰한 다음 재시도 여부를 판단한다. [브라우저 연동](tools.md#브라우저-연동)

## 부분 효과 확인

실패·취소 전까지 수행한 효과를 확인한 뒤 다음 작업을 결정한다. 셸 실행 이전의 파일 관찰은 오래된 상태로 표시하고, 불확실한 실행은 실제 상태를 확인한 후 이어간다. [셸과 파일 작업](tools.md#셸과-파일-작업) · [출력과 저장](runtime.md#출력과-저장)

Linux·WSL·macOS의 DNS·네트워크·인증 서비스·터미널 동작은 해당 환경에서 [플랫폼 실행 검사](development.md#플랫폼-실행-검증)로 확인한다. 호스트 DNS 설정 파일에 접근할 수 있다는 사실과 외부 도메인 조회 성공은 다르며, 교차 빌드는 해당 OS의 실제 실행 검사를 대신하지 않는다.
