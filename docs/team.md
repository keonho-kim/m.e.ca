# 팀 모드

[문서 목록](README.md) · [사용 가이드](usage.md) · [실행 경계](execution-boundary.md)

팀 모드는 같은 프로젝트에서 여러 에이전트가 공용 대화와 담당 범위를 공유하며 협업하는 기능이다. tui와 full 모두에서 사용할 수 있다.

## 시작과 참여

현재 대화에서 `!team`을 켠 뒤 요청한다. WebUI는 컴포저의 팀 버튼이나 설정에서 전환한다. 선택은 현재 대화에 저장하며 실행 중 변경은 다음 요청부터 적용한다.

```text
!team
API 구현과 테스트를 나눠서 진행하고 결과를 함께 검토해줘.
```

독립 세션 두 개로 시작한다. 팀원은 작업에 따라 동료를 초대·복구하며, 동시 참여 규모는 요청 예산과 가용 자원에 따라 달라진다. 각 참여자는 개인 대화·Thinking·문맥을 가지며 같은 프로젝트와 모델 연결을 사용한다. 서버의 `--concurrency`는 사용자 작업 수에 적용한다.

초대 전에 팀 현황과 공용 대화에서 현재 팀원들의 담당 업무, 명령 진행 상황과 대기 사유를 확인한다. 바로 맡을 수 있는 동료와 먼저 조율하고, 판단이 어려우면 해당 동료에게 `discuss`로 확인한다. 즉시 시작할 수 있는 독립 작업에 담당자나 진행 중인 초대가 없고 현재 팀원이 바로 맡을 수 없을 때 한 명을 초대한다.

`add_team_member`의 `domain`에는 같은 작업에 재사용할 공용 키를 넣는다. 해당 작업의 공용 `discuss` 제안이 있으면 그 순번을 `work_ref`로 전달한다. 키나 제안 순번이 현재 담당 또는 진행 중인 초대와 겹치면 기존 상태를 반환한다. 초대는 공용 대화에 남고 즉시 확인할 대상은 초대받은 동료로 지정한다.

## 개발 절차

참여자는 요구사항·담당 범위·공유 규약·선행 조건을 공용 대화에서 조율한다. 한 참여자의 일방적인 선언을 전체 합의로 간주하지 않는다. 공통 선행 작업과 경계 변경은 담당자를 정해 처리한다.

`set_work.domains`에는 현재 담당하는 독립 작업의 키와 확인된 `work_ref`를 함께 적는다. 한 팀원이 여러 도메인을 맡을 수 있다. 생략하면 이전 담당 정보를 유지하고, 빈 배열로 작업 담당을 해제한다. `paths`는 파일 변경 범위를 관리한다.

합의한 범위에서 작업하고 관련 변경·실패·완료 근거를 공유한다. 모델의 업무 분할이나 역할 이름이 구현 정확성을 보장하지는 않는다. 사용자 지시와 실제 파일 상태가 작업 판단의 기준이다.

## 대화와 도구

팀 참여자는 공통 도구와 팀 전용 도구를 사용한다. 호출 이름과 역할은 [전체 도구 목록](tools.md#도구-목록)에서 확인한다.

공개 발언은 작성자와 출처를 유지한다. `reply_to`로 관련 발언에 답하고 `mentions`로 확인할 동료를 지정할 수 있다. 발언만으로 다른 동료의 실행·업무 배정·사용자 승인을 확정하지 않는다. 개인 Thinking과 내부 모델 문맥은 공개 팀 스트림에 포함하지 않는다.

동료의 변경·도구 진행·결과를 읽고 같은 내용을 반복 실행하지 않도록 조율한다. 현재 담당 정보는 관련 작업의 판단을 돕는 정보이며 완료 증명이 아니다.

## 공유 프로젝트와 승인

같은 파일·겹친 경로의 변경은 실행 시점에서 조율한다. 관련 파일 상태가 바뀌면 아직 실행하지 않은 후보를 재검토한다. 독립 작업은 병렬로 진행할 수 있다.

프로젝트는 OS 격리 경계가 아니다. 패키지 설치·빌드·임의 셸 명령이 공유 자원에 미치는 효과는 참여자가 조율해야 한다. 파일·셸·외부 전송은 단일 모드와 같은 승인 정책을 적용한다. [승인과 보장 범위](execution-boundary.md)를 따른다.

## 종료와 재개

참여자는 남은 명령·관련 피드백·작업 결과를 확인하고 종료한다. 사용자 중지나 예산·오류 중단은 확인한 부분 결과를 보존하며, 불확실한 효과를 자동 재실행하지 않는다.

저장 대화를 재개하면 팀 선택과 참여자 기록을 복원한다. 복구가 끝난 작업의 정확성을 인증하거나 이전 프로세스를 그대로 되살리는 것은 아니다. 새 요청과 현재 프로젝트 상태를 기준으로 이어간다.

## 화면

공용 응답·업무·도구 결과는 발신자를 구분해 표시한다. 재시도·스킬 읽기 같은 알림과 완료 통계는 답변 본문과 분리한다. 팀 입·퇴장은 제어 정보이며 통계 행에 자유 문장으로 넣지 않는다.

토큰과 지원되는 비용은 실제 보고된 사용량을 합산한다. TUI 우상단에는 가장 최근에 시작한 활성 팀원의 호출 속도를 이름과 함께 표시하고, 작업 완료 요약에는 팀의 측정된 출력 토큰 수와 호출 시간 합계로 계산한 평균을 표시한다. 계산·표시는 [사용량 안내](usage.md#화면과-사용량)를 따른다.

## 프롬프트와 저장

팀 시스템 지침은 공통 작업 지침과 협업 규칙을 사용하고 팀 개발 지침은 설계·합의·구현·검증을 연결한다. 설치·업데이트의 프롬프트 처리와 사용자 수정 범위는 [설정 가이드](configuration.md#프롬프트와-compaction)를 따른다.

사용자 대화와 공용 기록, 참여자의 개인 기록은 관련 세션 그룹으로 보존한다. 공용 원문은 참조로 연결하므로 백업·복원에는 사용자 DB뿐 아니라 해당 팀 하위 폴더도 포함한다. [세션 보존](configuration.md#세션-저장과-복원)을 따른다.

## 자원 관리

참여자는 독립 실행 상태를 가지며 사용자 요청의 모델 호출·시간 예산을 공유한다. 공용 대화·개인 문맥·화면 투영은 각각의 목적과 수명을 유지하고 원문을 불필요하게 복제하지 않는다. 동시 작업과 읽기·표시 한도는 [설정](configuration.md)과 [서버 계약](server.md#이벤트재접속수명)을 따른다.

모델에 반복 제공되는 팀 요약은 UTF-8 기준 최대 256KiB다. 활성 팀원, 업무 참조와 명령 진행 상태를 앞부분에 제공한다. 요약이 줄어들면 `list_team_members`에서 담당 도메인과 경로를, `read_team_messages`에서 공용 기록을 확인할 수 있다.

공용 기록을 팀원에게 전달할 때 텍스트와 이미지가 16MiB 수신 예산을 함께 쓴다. 단일 항목이 한도보다 크면 빈 배치에서 원본 한 건을 전달할 수 있다. 2MiB 공용 캐시에는 보유 중인 이미지와 협업 메타데이터 크기도 반영한다. 팀원은 실제로 요약이 필요한 시점에 조립하고 응답 뒤 대기할 때 파생 요약을 회수한다.

초대 시 현재 팀원에게 다음 결정을 할 호출 예산을 남겨두고 새 팀원의 첫 호출을 예약한다. 예산 여유가 부족하거나 시스템 메모리 압박이 감지되면 기존 팀이 계속 작업할 수 있도록 초대를 보류한다. 합류가 취소되거나 팀원이 첫 호출 전에 종료하면 예약을 반환한다.

남은 호출이 모두 첫 호출 예약에 잡혀 있으면 기존 팀원의 요청은 예산 반환·소진 또는 요청 취소를 기다린다. 유휴 팀원이 작업을 재개할 때 공용 기록을 확인한다. 파일 변경 경로 추적은 1MiB를 넘기기 전에 상세 기록을 정리하고, 정리된 변경보다 오래된 결정에는 현재 파일을 다시 확인하도록 요구한다.

서로 독립적인 초대의 개인 DB 준비는 겹쳐서 진행할 수 있다. 합류 직전에 최신 사용자 지시와 작업 담당을 다시 확인한다. 준비 중 기존 팀원이 작업을 맡으면 새 세션을 시작하기 전 미사용 준비 자원과 호출 예약을 반환한다.

공용 원문 참조와 동시 출력 수집의 담당 코드는 [팀 실행과 공용 기록](optimization-strategies.md#팀-실행과-공용-기록)에서 확인한다.
