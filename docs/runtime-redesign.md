# 경량 실행 루프와 Conclave 재설계

2026-10-14 · 사용자 승인 후 핵심 구조 구현

사용자 승인에 따라 단일 실행·reason 통합·단일 Conclave·문맥 축소·조기 압축을 구현했다. 현행 계약은 [runtime.md](runtime.md), 설정은 [configuration.md](configuration.md)가 설명한다. 아래에는 설계 근거와 목표를 보존한다. 서버 문법 강제 자동 협상, Provider 공통 tokenizer, 사용자 승인형 검사 대체 UI는 후속 과제로 남으며 구현됐다고 간주하지 않는다.

목표는 작은 모델이 다음 행동을 선택하기 쉬운 구조와, 그 선택이 틀려도 안전하게 복구되는 실행기다. 가장 먼저 모델 호출 수와 반복 문맥을 줄인다. 속도 개선치는 동일 조건의 재시험으로 확인하며, 절감 예상치를 실측 결과로 표시하지 않는다.

## 2. 권고 구조

**사용자 요청 → 메인 모델 → native 호출 → 런타임 검사 → 필요한 변경 심사 → 사용자 승인 → 실행 → 결과 → 메인 모델**

- 세션당 실행 루프 하나를 유지한다. 모델은 현재 요청과 관측 결과를 보고 다음 도구 또는 답변을 선택한다.
- 내부 Goal 생성, Task 분해, inspect/work/answer 전환, Task별 응답, 별도 최종 보고 모델 호출을 제거한다.
- 첫 native 호출을 분류용으로 버리지 않고 같은 호출을 검증·실행한다. 인사도 같은 첫 요청에서 바로 답한다. 별도의 의도 분류 모델을 추가하지 않는다.
- 일반 모드에는 Scope와 실제 정책상 가능한 도구를 제공한다. 내부 하위 작업의 이름 때문에 수정 도구가 사라지는 경로를 없앤다.
- `!plan`은 사용자 요청에 의한 별도 읽기 전용 모드로 유지한다. 사용자 승인 Plan의 revision·step 바인딩도 유지하되, 그 안에 Goal/Task를 다시 생성하지 않는다.
- native 도구 호출은 한 번에 하나씩 실행한다. 여러 호출은 전체를 교정 대상으로 반환한다.

런타임에는 `request_message_id`, 실행 상태, 변경 revision, 미해결 검사, 호출·시간 예산, 실행 중인 후보만 남긴다. 실행 식별자는 취소·저장·복구를 위한 ID이며 작업을 분해하는 계층이 아니다. 현재 요청은 대화와 실행 체크포인트에 보존하되 모델 입력에서는 중복을 줄인다.

### 응답과 종료

- 메인 응답의 `DONE/WAIT/CONTINUE` 문자열 프로토콜을 제거한다. 도구가 있으면 실행 루프를 계속하고, 도구가 없는 답변은 턴 종료 후보로 처리한다.
- 진행 설명은 native 호출과 함께 온 assistant 본문으로 표시한다. 별도 진행 설명 호출을 강제하지 않는다.
- 읽기 전용 답변은 정상 종료한다. 조회 성공은 데이터 획득의 증거이며 계산 결과 전체의 검증 증명은 아니다.
- 변경 후 필수 검사가 남으면 구체적인 항목을 한 번 반환해 검증 또는 차단 사유 설명을 요청한다. 여전히 실행할 수 없으면 `unverified`/`blocked`로 종료하고 미해결 상태를 보존한다. 답변만 반복하는 루프를 만들지 않는다.
- 완료 판정은 모델 문구와 분리한다. 검사 실패가 남은 답변을 `verified`로 표시하지 않는다. 교정 후에도 성공을 잘못 주장하면 그 답변 대신 런타임이 관측된 미검증 상태를 안내하고 원문은 감사 기록으로 남긴다.
- Plan 초안은 Plan 모드 전용 `submit_plan` native 제어 함수로 저장한다. 일반 대화는 그대로 답하고, 승인 가능한 초안은 별도 명확한 이벤트로 전달한다. 제어 함수는 파일·셸 권한을 부여하지 않는다.

별도 분류 모델이나 도구 검색 모델은 또 다른 왕복을 만들기 때문에 초기 구조에 넣지 않는다. 모델 심사를 완전히 없애는 안은 현재 Conclave 안전 정책을 크게 바꾸므로 이번 권고에서는 단일 심사 게이트를 유지한다. 단일 심사의 부당 거절·결함 누락이 기준을 만족하지 못하면 속도 개선만으로 출시하지 않는다.

## 3. Self-grounding: 별도 호출을 없애고 사실과 의도를 분리

모든 native 도구 스키마에 짧은 `reason` 문자열을 공통 메타데이터로 포함하는 방식을 권고한다. 모델은 실제 인자와 이 한 문장을 같은 호출에서 생성한다. 필드별 질문이나 별도 근거 생성 호출은 없다.

- 모델이 제공하는 것: **왜 이 작업이 필요한지**에 대한 짧은 주장 하나.
- 런타임이 제공하는 것: 원본 요청 참조, 이미 관측한 파일·범위·snapshot, 호출 ID·인자 digest, 현재 정책·검증 상태.
- 아직 읽지 않은 파일은 관측 여부를 `unknown`으로 남긴다. 신규 파일 생성처럼 사용자 요청 자체가 근거인 작업도 허용한다.
- 필수 메타데이터가 유효하면 정확한 호출에 바인딩해 도구 준비 전에 저장한다. `reason`은 실행 어댑터의 실제 파일/셸 인자와 분리하며 승인·Scope를 대체하지 않는다.
- UI는 내부 근거 메타데이터를 일반 도구 인자와 분리한다. 모델 문맥에는 native 호출 안의 근거와 필요한 관측 참조를 한 번만 전달한다.
- 길이는 한 문장·최대 256문자, UTF-8 바이트 상한도 명시한다. 스키마와 로컬 검증의 문자/바이트 계약을 맞춘다. 누락·잘못된 타입은 기존 native 인자 오류 결과로 교정한다.
- Evidence/Action/Verify를 따로 생성하던 모델 호출, 3행 파서, grounding 전용 추론 역할·프롬프트를 제거한다. 근거의 영속화와 호출 바인딩은 유지한다.

이 변경은 기존의 “도구마다 별도 모델 호출로 세 항목 생성” 규칙을 대체하는 제안이다. 모델의 의도를 기록하는 목적은 유지하면서, 근거 생성 단계의 산술 오류나 XML 출력이 독립적인 실행 장벽이 되는 문제를 줄인다.

## 4. Conclave: 투표보다 작은 변경 심사

### 심사 수와 책임

**내용 변경 후보당 동일 모델의 짧은 심사 1회**를 기본으로 권고한다. 75줄당 3표·최대 12표·2/3 정족수 규칙을 대체한다. 같은 모델의 반복 투표가 같은 오판을 반복한 실측과 서버 큐 비용을 반영한 결정이다. 단일 심사가 항상 더 정확하다는 주장은 아니며, 결함 누락률을 별도로 검증한다.

| 경계 | 책임 |
| --- | --- |
| 런타임 사전 검사 | 스키마, Scope, Plan 제한, snapshot·anchor, 파일 버전, 실제 diff와 변경량 |
| Conclave | 사용자 의도에 맞는 후보인지, 명확한 결함·불필요한 변경이 있는지, 사후 검증 계획이 타당한지 |
| 사용자 승인 | 이 후보의 실제 변경·명령을 허용할지 |
| 실행 후 검사 | 실제 적용 결과, 테스트 종료 상태와 결과, 변경 revision에 맞는 검증 |

- 내용 변화가 없는 후보·빈 파일·빈 폴더 생성은 기존처럼 LLM 심사를 생략한다. 사용자 승인 정책은 계속 적용한다.
- 기존 파일을 비우는 작업과 내용 삭제는 내용 변경으로 심사한다.
- 명령의 임의 부작용을 파일 diff 심사로 보증하지 않는다. 기존 셸 Scope·승인·전용 파일 도구 유도 정책을 유지한다.
- “아직 실행되지 않음”과 “실행 후 테스트가 아직 없음”은 실행 전 심사의 정상 상태다. 이미 알려진 관련 실패나 기존 오류는 관측 사실로 제공한다.
- 규모가 큰 변경은 심사 모델 수를 늘리는 대신 후보를 나눈다. 문맥에 담지 못한 변경을 일부만 보고 전체 통과시키지 않는다.

### 심사 입력

전용 입력 객체 한 개를 구성한다. 메인 대화·native 호출 이력 전체·이전 심사 장문을 그대로 복사하지 않는다.

1. 원본 사용자 요청과 활성 제약.
2. 프로젝트 AGENTS.md의 적용 지침 원문. 명시적으로 구획된 적용 범위가 없는 지침은 임의 추출·요약하지 않는다.
3. 후보의 경로, 변경 유형, 검증된 before/after 버전과 **변경 diff 한 벌**.
4. 필요한 주변 코드·이미 관측된 관련 근거의 참조와 해당 부분.
5. 런타임이 계산한 줄 수, 추가/삭제량, 파일 존재, EOF 개행 여부 등 사실.
6. 짧은 모델 의도와 예정된 사후 검증. 검증 계획은 실제 통과와 구분한다.

전체 `write_file.content`와 동일 내용을 가진 diff를 중복 전달하지 않는다. 해시는 바인딩 값으로만 사용하며 모델이 해시 차이에서 의미를 추론할 이유를 없앤다. 관련 근거가 부족하면 `needs_context`로 요청하고 범위가 검증된 조회만 수행한다.

### 심사 출력과 복구

영어 내용의 작은 구조화 결과를 사용한다. 예시는 아래와 같으며 최종 JSON Schema는 구현 단계에서 고정한다.

```json
{
  "decision": "reject",
  "findings": [
    {
      "path": "settings.txt",
      "side": "after",
      "line": 7,
      "reason": "The requested value differs from the proposed value."
    }
  ],
  "context_requests": []
}
```

- 판정은 `pass`, `reject`, `needs_context`. `reject`는 최대 3개의 구체적 지적과 실제 후보·요청·관측을 가리키는 유효한 참조가 필요하다. 예시의 파일/줄 참조 외에도 사용자 요구나 관측 ID를 참조할 수 있도록 스키마를 구분한다.
- 코드가 참조 대상·줄 범위·후보 버전을 검증한다. 참조가 맞는다는 사실만으로 지적의 의미적 정확성이 입증되는 것은 아니다.
- `needs_context`의 추가 조회·재심사는 최대 한 번으로 제한한다. 여전히 판단이 불가능하면 `review_incomplete`로 차단하고 더 작은 후보나 사용자 정보를 요청한다.
- 형식 교정도 최대 한 번이며 같은 재심사 예산을 공유한다. 한 후보의 총 모델 심사는 정상 1회, 추가 1회까지다. 전송 실패 재시도는 별도 제한된 전송 정책과 전체 예산에 포함한다.
- 구조화 출력은 해당 Provider·endpoint·모델 조합에서 검증된 경우에 사용한다. 구조화 출력 미지원이 확인된 조합은 같은 작은 JSON 계약과 로컬 엄격 파서를 사전에 선택한다. 인증·연결·추론 인자 오류를 기능 미지원으로 취급해 요청 필드나 endpoint를 조용히 바꾸지 않는다. 일반 본문 속 임의 JSON을 도구 실행으로 해석하는 경로는 추가하지 않는다.
- 심사 오류·미완료·유효하지 않은 판정은 실행을 차단한다. 빠르게 처리하기 위해 통과로 바꾸지 않는다.
- 같은 원본 버전·변경 내용·요청·지침·근거·모델 설정의 후보에는 실행 중 이미 얻은 심사를 재사용한다. 새 Call ID나 설명 문구만 바꾼 반복은 새로운 진전으로 취급하지 않는다. 새 근거나 실제 변경이 있어야 재생성이 진전이 된다.
- 심사 재사용은 모델 의견의 재사용이다. 실제 실행에는 매번 새 후보 바인딩, 현재 Scope·파일 버전 검사와 필요한 사용자 승인이 적용된다. 재시작 뒤 심사 기록으로 변경을 자동 실행하지 않는다.

단일 심사·문맥 요청·구조화 결과·유한 재심사는 기존 투표 정책과 다른 명시적 정책 변경이다. UI에는 기존처럼 Pass/Fail과 필요한 짧은 차단 사유만 표시한다.

## 5. 입력 토큰 관리

### 먼저 줄일 항목

- 중복된 기본 시스템 프롬프트와 runtimeProtocol을 하나의 짧은 규약으로 정리한다. 프로젝트의 개발 원칙은 프로젝트 지침을 우선하고, V의 기본값은 간결한 공통 원칙만 제공한다.
- 도구 설명은 기능·필수 조건·실패 시 행동에 집중한다. 반복되는 승인·Scope 설명은 공통 규약 한 곳에 둔다. 현재의 작은 고정 도구 목록에는 별도 도구 검색 모델이나 lazy-loading 왕복을 추가하지 않는다.
- 현재 요청, 파일 본문, 도구 결과, 모델 근거, 검증 상태를 native 이력과 Current facts 양쪽에 복제하지 않는다. 최신 미해결 상태만 별도 사실로 전달한다.
- 무진전 카운터·내부 ID·전체 승인 스냅샷처럼 다음 선택에 필요 없는 값은 감사 기록에 보존하고 평상시 모델 문맥에서 제외한다. 제한 임박·차단처럼 행동을 바꾸는 시점에만 안내한다.
- 내부 심사에는 별도 작은 문맥을 제공한다. 메인 모델에는 압축 전 전체 대화와 유효한 native 호출·결과 쌍을 유지한다.

### 같은 읽기 결과의 반복

실제 파일·버전·범위를 다시 확인한 결과가 같고, 최초 본문이 현재 모델 문맥에 남아 있다면 새 도구 결과는 `unchanged`와 최초 호출 참조로 반환한다. Scope 확인과 파일 최신성 검사는 매번 수행한다. mtime만을 동일성 증거로 사용하지 않는다.

압축으로 최초 본문이 문맥에서 사라졌다면 참조만 보내지 않고 이번 결과에 본문을 다시 제공한다. 원본 이력은 그대로 남는다. 이 방식은 이미 생성된 대화를 몰래 삭제하는 것과 구분한다.

파일은 필요한 범위로 읽고 큰 프로세스 출력은 명시된 발췌·실패 진단을 전달한다. 전체 로그가 필요한 경우 승인된 명령으로 프로젝트 로그 파일에 저장한 뒤 기존 범위 읽기를 사용한다. 초기 구현에 별도 벡터 DB·repo map·새 로그 검색 서비스를 추가하지 않는다.

### Compaction

- 기존 `threshold_tokens=256000` 누적 트리거는 유지하고, **현재 문맥 크기에 따른 조기 압축 트리거**를 추가하는 안을 권고한다.
- 제안 작업 문맥 목표는 입력 **16,384토큰**이다. 이는 아직 벤치마크로 확정한 값이 아니며 모델의 실제 context와 출력 여유를 함께 고려해 설정 가능하게 한다.
- tokenizer API가 있으면 도구 스키마까지 포함한 정확한 요청 토큰을 사용한다. 없으면 마지막 실제 input usage를 관측값으로 사용하며, 다음 요청의 정확한 토큰 수라고 표시하지 않는다. 입력 증가에는 별도 바이트 안전 한도를 적용한다.
- 실제 context 오류는 안전한 결정 경계에서 압축한 뒤 생성 요청을 제한적으로 재시도한다. 이미 수행한 도구를 재실행하지 않는다.
- 압축은 오래된 완료 이력을 우선 대상으로 삼고 최근 대화·현재 요청·미해결 검사·승인 대기·관측된 변경을 보존한다. 최근 구간과 요약을 합쳐 다음 문맥을 구성하고 전체 원문은 세션 저장소에 유지한다.
- Frontier tree는 미해결 요구·변경·검증 근거를 보존하는 요약 작성법으로 유지한다. Goal/Task 스케줄러나 별도 실행 계층으로 사용하지 않는다.
- 프로젝트 AGENTS.md 원문과 활성 권한·승인 계약은 압축으로 바꾸지 않는다. 고정 지침 자체가 목표 문맥보다 크면 이를 명시하고 실제 모델 한도 안에서 처리한다. 한도를 넘으면 설정·지침 조정이 필요하다는 오류를 반환한다.
- 이 조기 트리거는 기존의 누적 임계값만 사용하는 정책에 대한 추가 제안이다. 설정 의미를 바꾸거나 과거 메시지를 조용히 잘라내지 않는다.

### 캐시와 측정

안정적인 시스템 지침과 스키마를 prefix에 두고 가변 상태는 뒤에 둔다. 서버 prefix cache는 보조 최적화이며 입력 토큰 절감과 계산량 절감을 구분한다. vLLM의 APC는 공통 prefix의 KV 재사용으로 재계산을 줄이는 기능이다. [공식 설명](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/).

UI의 INPUT/OUTPUT은 계속 실제 수신 usage만 집계한다. 요청 크기, 실제 usage, 첫 토큰 시간, 전체 생성 시간, 심사 큐 대기, 재시도 수를 별도로 측정한다. 서버가 제공하지 않는 캐시 절약량·토큰 수는 만들어 넣지 않는다.

## 6. 검증과 실패 복구

- 읽기·검색 실패는 관측 오류다. `purpose=check`라는 모델 선언만으로 영구 필수 검사를 생성하지 않는다. read/search의 목적 필드는 제거하고 실제 효과·원본 요구와 결과로 다룬다.
- 실행 전에 거절된 스키마·잘못된 대상 유형은 검사 실행과 구분한다. 같은 잘못된 도구를 성공시켜야만 빠져나오는 상태를 만들지 않는다.
- 실제 검사 명령의 실패는 해당 변경 revision의 검증 기록으로 보존한다. 실패한 테스트를 다른 성공으로 덮지 않는다.
- 현재 검사는 도구·명령 해시와 Call ID·revision을 사용한다. 사용자 승인형 검사 대체 관계는 후속 과제이며 실제 실패를 임의로 해소하지 않는다.
- 코드가 판별할 수 있는 실행 전 오류만 자동 정리 대상으로 삼는다. 실제 실패한 검사의 의미를 바꾸거나 요구를 폐기하는 변경에는 사용자 지시 또는 승인된 Plan 변경이 필요하다. 모델이 `true` 같은 무관한 성공으로 기존 실패를 해소할 수 없게 한다.
- 필요한 검증을 실행할 수 없는 경우 상태는 `unverified`/`blocked`다. 이를 성공으로 기록하지 않으면서도 사용자에게 결과와 이유를 반환하고 턴을 끝낼 수 있다.
- 무진전은 같은 파일 버전·관측 결과·미해결 오류를 기준으로 판단한다. Call ID·reason 문구·같은 결과의 다른 조회 옵션만 바뀌는 것은 진전이 아니다. 실제 버전 변경이나 새 범위의 관측은 진전으로 인정한다.
- Scope·승인 거절은 추가 우회 실행을 유도하는 일반 실행 오류와 구분한다. 정책 변경은 명시적 사용자 작업으로만 수행한다.
- 전송 오류, 인자 오류, 심사 오류, 실제 검사 실패, 사용자 취소의 복구 경로를 분리한다. 모든 경로는 같은 실행 예산과 단일 부작용 실행 규칙을 공유한다.

## 7. 호출별 추론 설정

| 역할 | 제안 | 유지할 값 |
| --- | --- | --- |
| 메인 에이전트 | 사용자 Thinking/effort 선택을 따름 | temperature 0.7, max_output_tokens 25600 |
| Plan | 읽기 전용 대화와 native Plan 제출 | temperature 0.7, max_output_tokens 12800 |
| Conclave | OFF 지원이 검증된 모델에서는 역할별 Thinking OFF 권고 | temperature 0.4, max_output_tokens 12800 |
| Compaction | 짧은 보존 요약; 역할별 Thinking OFF 권고 | temperature 0.2, max_output_tokens 12800 |
| 연결 진단 | 제어 기능을 검증하는 현재 별도 흐름 유지 | temperature 0.2, max_output_tokens 12800 |

Goal·grounding·별도 report 역할은 호출자가 없어지므로 제거한다. 출력 상한을 낮춰 얻는 효과를 이번 설계의 전제로 삼지 않는다. Conclave는 짧은 결과 스키마와 적은 호출 수로 실제 출력량을 줄인다.

역할별 Thinking은 현재의 전역 선택 상속과 다른 제안이다. OFF 미지원 모델에 OFF를 조용히 전송하거나 다른 값으로 치환하지 않는다. 해당 조합을 명시적으로 안내하고 지원되는 선택을 사용해야 한다. 주 모델의 Thinking 선택과 역할별 설정은 각각 표시·검증한다.

LM Studio의 공식 구조화 출력 설명은 `/v1/chat/completions`에 대한 JSON Schema 지원이다. 현재 사용하는 Responses endpoint에 같은 필드가 적용된다고 가정하지 않는다. 구조화 심사를 위해 endpoint를 분리한다면 provider의 명시적 내부 역할 어댑터와 실제 기능 검증으로 처리한다. [LM Studio 문서](https://lmstudio.ai/docs/developer/openai-compat/structured-output).

## 8. 책임과 저장 구조

| 소유자 | 변경 방향 |
| --- | --- |
| `agent/run` | 단일 실행 수명·native 호출·정책·승인·예산·종료 상태 |
| `agent/tool`, `tools/local` | 공통 reason 메타데이터 검증, 실제 실행 인자와 분리, snapshot·diff 사실 |
| `agent/grounding` | 별도 생성 없이 호출에 묶인 의도·관측 참조 기록 |
| `agent/conclave` | 후보 입력 구성·단일 심사·구조화 판정·제한된 재심사 |
| `agent/context` | 한 번씩 전달하는 이력·현재 사실, 역할별 문맥 선택 |
| `agent/verification` | 관측 오류와 검사 상태 분리, 검사 식별·대체 근거·revision |
| `agent/progress` | 실제 새 관측·변경 기준의 반복 감지 |
| `agent/compact` | 원문 보존·증분 요약·현재 문맥 압력 처리 |
| `agent/plan` | 사용자 승인 Plan 계약과 상태 전이 |
| `storage/history`, `storage/recovery` | 실행 사실 저장, 중단 복구, 부작용 재생 방지 |
| `provider/protocol` | 검증된 native·structured 계약 변환 |

`agent/goal`과 Goal/Task orchestration을 삭제한다. 기존 이름의 전달 패키지를 남기지 않는다. Monitor의 별도 모델 호출은 없으며, 추가 관측 goroutine 대신 이미 존재하는 실행 worker에서 사실을 기록·투영하는 단순 모듈을 권고한다. 사전 실행 기록과 결과의 영속화 보장은 유지한다. UI event loop에 DB·모델 I/O를 옮기지 않는다.

새 프레임워크·의존성·서비스를 도입하지 않고 기존 Go 함수·struct·consumer-owned I/O 계약을 사용한다. 심사 결과 재사용은 한 실행이 소유하는 작은 bounded map으로 제한하고, 실행 승인을 캐시하지 않는다.

저장 계약에서 Goal/Task 필드가 사라지면 지원 스키마 버전을 올린다. 기존 DB 파일은 보존하고 미지원 스키마를 명시적으로 거부한다. 자동 마이그레이션이나 파일 삭제를 넣지 않는다. 폐기된 TOML 역할 섹션은 명시적으로 정리하며, 모델 연결·키 참조를 보존한다. 사용자 소유의 기존 goal/grounding 프롬프트 파일은 사용 대상에서 제외하되 자동 삭제하지 않는다.

## 9. 검증 목표와 구현 순서

아래 수치는 제안하는 합격 기준이며 현재 달성 결과가 아니다. 동일 모델·양자화·context·서버 병렬도·Thinking 설정을 기록하고, 준비된 최소 사례를 각각 5회 실행한다. cold/warm을 구분하며 테스트 측 중단 시간을 제품 실패 종료와 따로 기록한다.

| 항목 | 제안 합격 기준 |
| --- | --- |
| 인사, 프로젝트 AGENTS 없음 | 생성 1회, INPUT 2,500 이하, 불필요한 도구 실행 0 |
| 간단 CSV 읽기 | 생성 2~3회 목표, 정답 3/9/40, 잘못된 탐색 실패 후에도 정상 종료 가능 |
| 단일 README 생성·검사 | 생성 6회 이하 목표, golden bytes 일치, 승인·실제 검사 완료 |
| 한 줄 버그 수정 | 생성 8회 이하 목표, 원래 테스트 보존·통과, EOF 개행 보존 |
| 형식 오류 | 명시적 오류와 유한 교정, 잘못된 후보 실행 0 |
| Scope·Plan·버전 가드 | 미승인·범위 밖·오래된 후보 실행 0 |
| 심사 정확성 | 정상 후보의 부당 거절과 결함 후보의 오통과를 별도 기록; 속도만으로 합격 처리하지 않음 |
| 중단·재시도·재개 | 이중 실행 0, lease 해제·원문·검사 상태 보존 |
| 긴 대화 | 압축 전후 요청·제약·실패한 검사·수정 파일·최근 필요한 코드 보존 |

호출 수 예시: 읽기→수정→검사→답변을 한 번씩 하는 정상 단일 실행은 메인 4회다. 현재 별도 grounding 3회와 심사 3회면 최소 10회가 되고 Goal 계층은 추가 비용을 만든다. 권고안은 메인 4회+심사 1회=5회다. 이는 복구·추가 조회가 없는 구조상 예시이며 실제 지연의 절반을 보장하는 수치는 아니다.

1. Goal/Task·텍스트 제어 헤더를 제거하고 단일 루프·종료 상태를 먼저 검증한다.
2. reason 통합으로 별도 grounding 호출을 제거한다. native 오류·근거 저장·승인 바인딩을 회귀 검증한다.
3. Conclave를 작은 입력의 단일 심사로 교체하고 정상/결함 후보의 판정 데이터를 비교한다.
4. 검사 상태와 실패 복구를 정리하고 실제 수정·승인·검증 완료를 확보한다.
5. 프롬프트·이력 중복·반복 읽기를 줄이고 현재 문맥 기반 압축을 추가한다.
6. 로컬 실측과 Provider 계약 테스트를 다시 수행한다. 변경된 제품 계약·AGENTS.md·설정·프롬프트·스키마를 함께 갱신한다.

처음부터 모든 최적화를 함께 넣기보다 단계별로 같은 사례를 비교한다. 빠른 실패를 빠른 성공으로 오해하지 않고, **성공 작업당 실제 input/output·호출 수·경과 시간**을 최종 평가 기준으로 삼는다.

- Plan 단계별 답변과 마지막 합친 답변이 이력에 이중 저장되는 경로를 제거했다.

- 단일 Conclave가 t24의 EOF 개행 제거를 놓쳤다. 해당 후보는 심사를 통과했고 실제 개행도 제거됐다. 사용자 요청의 한 줄 버그는 수정됐지만 EOF 보존 목표는 미달이다.

- 심사 정확성·장시간 압축 후 성공률·Provider 전체 실측은 별도 평가가 필요하다.

자동 검증은 전체 Go 테스트·vet·빌드, 전체 race 및 변경한 Provider/실행/저장/TUI 경계의 추가 race 검사로 수행한다. Scope·승인·Plan 제한·고아 호출·검사 실패 보존·중복 실행 방지·압축 시 원문 보존은 자동 회귀 테스트로 확인한다.


## 11. EOF·macOS 실행 문제 후속 수정

위 t24의 EOF 개행 누락과 macOS Python 실행 실패는 후속 수정으로 해결했다. 기본 format_policy=preserve로 후보를 고정하기 전에 기존 EOF/줄바꿈 형식을 보존하고, 실제 형식을 read_file 결과에 분리해서 제공한다. 명시적 literal 형식 변경은 심사와 승인에서 확인할 수 있다. 표시용 해시가 소스에 혼입되는 후보도 기본 차단하고, 앵커 오류 후 재조회에는 원문을 다시 제공한다.

macOS는 검증된 Apple 개발 도구 설치 경로를 읽기·실행 허용하고 DEVELOPER_DIR로 전달한다. 도구 탐지는 사용자 취소를 따르며, 전역 Xcode 선택이나 설치를 변경하지 않는다. 격리된 Git은 시스템·전역 설정을 제외한다. purpose=check는 실패를 숨기는 셸 연결을 거부한다. 격리 초기화에 실패한 명령은 실제 실행된 검사로 등록하지 않는다.

실모델 t27에서 모델의 앵커 오기와 표시용 해시의 소스 복사 제안을 발견해 승인 거절 후 해당 보호를 보강했다. t28에서는 잘못된 앵커를 재조회해 복구한 뒤 실제 한 줄 부분 수정과 사용자 승인 두 번을 거쳐 python3 -m unittest -v의 두 검사가 격리 안에서 통과했다. EOF 개행과 기존 테스트 파일을 바이트 비교로 확인했고 run 상태는 verified였다. 9회 호출, 전체 64.78초는 시험 준비·승인 대기를 포함하므로 순수 생성 지연으로 해석하지 않는다. Conclave의 일반적인 의미적 정확성이 증명된 것은 아니다.

Linux arm64에서도 사용자 도구 경로, 파일 격리, 커널·네트워크 제한, 취소 시 자식 정리의 실제 실행을 재검증했다. 테스트 컨테이너의 기본 proc 마스킹이 private proc 마운트를 거부하는 경우를 분리하고, 허용 환경의 성공 경로와 제한 환경의 무실행 실패 경로를 각각 확인했다. 상세 플랫폼 검증 범위는 development.md를 따른다.
