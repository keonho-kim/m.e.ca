# 사용 가이드

[← README](../README.md)

모델 연결, 키보드 조작, 승인과 Provider 연결 문제를 다룹니다.

## 처음 실행하기

첫 실행에서 사용자 홈의 `~/.v`에 기본 TOML 설정, 세션 DB 디렉터리, 로그 디렉터리를 준비한다. 기존 설정과 대화는 보존한다. 기본 정책은 `directory + approve`이며, 일반 시작은 해당 프로젝트의 최근 세션을 복구한다. 새 세션을 만들려면 `config.toml`의 `[session] restore_last = false`를 설정한다. `v resume`은 프로젝트와 관계없이 저장된 대화를 명시적으로 선택한다.

처음에는 `!model`로 Provider, Endpoint, API Key, 모델을 선택한다. 주소 필드는 실제 편집 커서와 가로 스크롤을 표시한다. `Ctrl+U`는 필드 전체를 지우고, 빈 주소·잘못된 URL은 다음 단계로 진행하지 않는다. 입력창은 사용자가 편집한 주소를 유지한다. OpenAI 호환 API의 `/v1` 경로는 HTTP 어댑터가 조립한다. Ollama, vLLM, SGLang, LM Studio, LiteLLM Proxy와 OpenAI 호환 서버의 실제 모델 목록을 조회한다. 조회 API가 없으면 Model ID를 직접 입력할 수 있다. 모델을 적용하기 전에 부작용 없는 일반 응답 진단을 수행한다. 실제 작업에는 native Tool Calling 지원과 서버의 모델에 맞는 Tool Parser 설정이 필요하다. 연결 진단 성공만으로 도구 호출 지원이 검증되는 것은 아니다.

선택한 모델의 식별 근거를 Provider별로 조회한다. `!model` 상단에는 서빙 별칭 오른쪽에 단일 원본 식별명을 흐린 글씨로 표시한다. 식별명은 단일 대상이 확인된 경우에만 표시한다. `!model → 모델 정보`에서 원본 선언·모델군·복수 대상·식별 불가, 적용 프로파일과 출처를 확인하고 `PgUp/PgDn`으로 스크롤한다. 서버가 검토된 원본 ID를 제공하면 임의 서빙 별칭에도 자동 매칭하며 실제 요청의 별칭은 유지한다. 여러 LiteLLM upstream·불완전한 정보에는 자동 특화를 적용하지 않는다. 메타데이터 조회가 불가능해도 대화 진단을 진행한다. 식별과 Thinking 제어 검증은 별개다. [Provider별 조회와 제한](model-profiles.md#provider별-원본-식별)을 참고한다.

서버가 SSE·NDJSON 스트림을 보내면 응답 본문과 Thinking을 도착하는 대로 갱신한다. 내부 `DONE`·`WAIT` 헤더, 도구 선택·인자 응답, 검증 전 완료 선언과 Plan 초안은 스트림 본문에 노출하지 않는다. 완료된 응답은 한 번만 기록하며 취소 시 마스킹된 부분 응답을 보존한다. 서버가 단일 JSON 응답을 보내면 완료 후 표시한다.

`!model`의 Provider 목록에서 **LiteLLM**을 선택할 수 있다. 기본 주소는 `http://localhost:4000/v1`이며 원하는 Proxy 주소로 바꿀 수 있다. API Key에는 해당 Proxy의 virtual key를 입력한다(인증 없는 Proxy는 비워 둔다). `/v1/models`가 반환한 모델 별칭을 그대로 선택하고 `/v1/chat/completions`로 스트리밍 요청을 보낸다. [LiteLLM Proxy 공식 문서](https://docs.litellm.ai/docs/proxy/docker_quick_start)의 HTTP API를 사용하며 별도 SDK를 설치하지 않는다. LiteLLM의 현재 `reasoning_content` 출력은 별도 Thinking으로 읽지만, 라우팅된 모델의 ON/OFF 제어를 추측하지 않아 토글은 미지원으로 표시한다. [추론 응답 규약](https://docs.litellm.ai/docs/reasoning_content)을 따른다. 실제 Proxy 배포와 연결 모델의 응답 품질은 별도 환경 검증 대상이다.

API Key는 OS 자격 증명 저장소에만 보관한다. Linux는 동작하는 D-Bus Secret Service, macOS는 Keychain이 필요하다. 저장소가 없거나 잠겨 있으면 연결 오류를 표시하며 평문 파일로 대체하지 않는다. 인증이 필요 없는 로컬 서버는 Key를 비워 둔다.

`!model`에서 선택한 마지막 연결은 새 세션에서도 재사용한다. 기존 세션에 저장된 모델이 있으면 그 선택이 우선한다. 연결 정보와 `.db.lock` 파일의 의미는 [설정과 대화 보존](configuration.md#모델-연결-재사용)을 참고한다.

## Linux의 프로젝트 셸

샌드박스 실행기는 V 바이너리에 포함된다. `v` 바이너리 안의 실행기가 Landlock·seccomp·네임스페이스를 사용하며, Bubblewrap·sudo·설치 질문은 없다. 빌드는 Go 도구 체인으로 수행한다.

Linux amd64·arm64에서 Landlock ABI 3 이상과 필요한 커널 기능이 활성화되어 있어야 한다. 비특권 user namespace, mount/PID/network/IPC/UTS namespace, seccomp, openat2·mount_setattr 등을 실제 실행 시 확인한다. 버전 번호만으로 지원을 단정하지 않으며, 컨테이너나 AppArmor 정책이 이를 막는 경우에도 프로젝트 셸은 `scope_unavailable`로 실패 이유를 반환한다. 호스트 정책을 자동 변경하거나 제한 없는 셸로 재시도하지 않는다.

앱 시작·대화·파일 도구는 이 기능의 유무와 관계없이 사용할 수 있다. `전체 시스템` Scope는 사용자가 직접 선택한 경우에만 기존 OS 사용자 권한으로 실행하며, 사용자 승인 정책은 그대로 적용한다. 자동 승인에서도 현재 Scope가 적용된다.

프로젝트 셸에는 프로젝트와 전용 임시 공간, 읽기 전용 시스템 실행 경로를 제공한다. 설치된 `~/.local/bin`과 `~/.local/share/uv/python`도 읽기·실행 전용으로 제공하며, 실행 PATH와 uv의 관리 Python 위치를 연결한다. 따라서 이 경로의 `uv`로 프로젝트를 생성할 수 있다. 홈 전체나 임의의 PATH 디렉터리, uv 인증·설정 디렉터리를 노출하지 않는다. 설치 디렉터리 자체가 심볼릭 링크로 다른 위치를 가리키면 오류로 거부하며, 내부 링크도 허용된 경로에만 접근할 수 있다. 캐시는 실행별 임시 공간을 사용한다. 프로젝트 밖 사용자 파일·V 상태·네트워크와 호스트 소켓 접근을 차단한다. 시스템 실행 영역이나 V 상태 내부, 실행 임시 공간과 겹치는 프로젝트 루트는 거부한다. 프로젝트 아래 별도로 마운트된 볼륨은 가져오지 않는다. macOS는 기존 시스템 Seatbelt를 사용한다.

## TUI 사용

대화는 `> 사용자 입력`, 빈 줄, `Agent`, 응답 순서로 누적된다. 응답과 다음 요청 사이에는 빈 줄 두 개를 두고, 장식용 ASCII 구분자 대신 왼쪽의 `>`·`Agent` 표시와 여백으로 구분한다. 새 입력창은 기록 바로 아래에 놓이고, 기록이 화면을 채우면 하단에서 입력한다. 모델·Thinking·Scope·자동 승인·PLAN 상태는 키맵 바로 윗줄에, 키맵은 맨 아랫줄에 고정한다. 상단 고정 입력 영역과 `Model answer; no tool execution.` 완료 문구는 표시하지 않는다. 도구·Thinking 기록은 해당 대화 안에서 순서대로 표시하며 이어하기에도 같은 형식을 사용한다. 검증 상태는 내부에 보존하고, 화면에는 실제 응답과 도구 결과를 표시한다. `!`·`@` 후보는 새 입력창 아래에 표시한다.

상단 오른쪽에는 `INPUT 12345 OUTPUT 6789`처럼 현재 대화의 누적 모델 사용량을 숫자로 표시한다. 스크롤·메뉴·파일 화면에서도 고정되고, 입력창은 대화 아래에 유지된다. vLLM·SGLang에는 `include_usage`와 `continuous_usage_stats`를 요청하고, LiteLLM·일반 호환 API에는 `include_usage`를 요청한다. LM Studio Responses의 실제 usage를 읽는다. Ollama는 native `prompt_eval_count`·`eval_count`를 읽는다. 중간 usage는 호출 전체의 최신값으로 교체하고 완료 시 한 번만 합산한다.

사용량은 Provider가 실제 전송한 수치만 반영한다. 수신 전에는 기존 숫자를 유지하며, 한 번도 수신하지 않았다면 `INPUT 0 OUTPUT 0`이다. 응답 텍스트나 Thinking 길이로 추정하지 않는다. usage를 전혀 받지 않은 호출은 사용량 기록을 만들지 않고, 수신 후 추가 텍스트가 오거나 호출이 중단되면 마지막으로 수신한 값만 한 번 기록한다. 서버가 보고하지 않은 사용량은 합계에 포함되지 않는다. 이전 추정 필드가 들어 있는 사용량 저장 형식은 명시적으로 거부하며 자동 변환·삭제하지 않는다. 출력 사용량은 reasoning을 포함한 completion 합계를 한 번만 집계한다. 일반 대화, 도구 결정·인자, Plan, Compaction 호출을 포함하고 연결·설정 진단은 제외한다. 사용량은 호출별 SQLite 이벤트로 저장하여 이어하기에서 복구한다. 사용량 합계는 집계 기록이 있는 호출부터 계산한다. Compaction의 256,000 토큰 발동 누적량과 별개다. 전체 숫자가 들어가지 않는 좁은 창에서는 통계를 생략한다.

사용량 API 근거: [Ollama](https://docs.ollama.com/api/usage), [LiteLLM](https://docs.litellm.ai/docs/completion/usage), [SGLang StreamOptions](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/entrypoints/openai/protocol.py), [vLLM 스트림 설정](https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/anthropic/serving.py).

모델 연결 시 짧은 일반 인사 요청으로 비어 있지 않은 응답과 정상 완료를 확인한다. 특정 문구·JSON·도구 이름·파일 경로를 정답으로 요구하지 않는다. Thinking ON/OFF와 강도 진단은 별도로 유지하며 서버의 chat template·reasoning parser 설정이 적용되는지 확인한다. 실제 작업의 native 도구 인자 검증과 교정은 작업 실행 중에 수행한다. 오류는 현재 화면에 한 번 표시한다.

`!new`는 실행 중인 작업을 취소하고 worker·연결·DB 잠금을 정리한 뒤 새 대화를 연다. 이전 대화는 보존하며 전역 모델 연결을 다시 사용한다. 대화·사용량·Plan·세션 정책 재정의는 새로 시작하고, Scope·Permission은 전역 기본값을 따른다.

Plan 모드에서도 인사·질문·중간 설명은 일반 대화로 처리한다. 매 응답에 계획을 요구하지 않으며, 계획이 없다는 이유로 오류를 내지 않는다. 목표와 단계가 모두 갖춰진 계획만 승인 화면으로 넘어가고, 그 전까지 기존 계획 상태와 읽기 전용 제한을 유지한다.

`!plan`을 다시 입력하면 현재 미승인 계획을 취소하고 일반 모드로 돌아간다. 생성 중이면 작업을 중단한 뒤 종료하며, 취소는 실행 승인이 아니다. 취소 상태는 저장되어 이어하기에서도 모드가 꺼진다. Plan 모드에서는 자동 승인 설정과 관계없이 파일 변경·생성·삭제·이동 및 셸 실행이 차단된다.

화면 하단 두 줄을 확보하여 모델·정책 상태를 윗줄에, nano 형태의 문맥별 키맵을 맨 아랫줄에 표시한다. 키는 굵게, 설명은 낮춘 농도로 표시하고 터미널 기본 배경을 유지한다. 스크롤과 화면 전환·리사이즈에도 위치를 고정한다. 너비가 부족하면 상태 행의 모델명을 줄이고 키맵 행에는 주요 키부터 표시한다. 각 행은 한 줄로 표시한다.

승인 diff의 추가·삭제 줄을 제외한 UI는 터미널 기본 전경·배경을 유지하고 배경색과 역상을 사용하지 않는다. 선택 항목은 굵은 글자, 나머지 후보와 Thinking 출력은 낮춘 글자 농도로 구분한다. 후보는 입력의 첫 명령 토큰을 작성할 때만 나타나며 자연어 본문·명령 인자·붙여넣기 중에는 열리지 않는다. 좁은 화면에서는 목록 높이를 제한하고 선택 항목을 따라 스크롤한다.

도구 기록은 다음처럼 왼쪽 들여쓰기로 이름·실제 인자·실제 출력을 구분한다. 이름은 두 칸, 인자·출력은 네 칸 들여쓰고 긴 줄의 감싼 행에도 들여쓰기를 유지한다. 실행 중에는 인자와 `Running…`을 임시로 표시하고, 완료되면 실제 결과 기록 하나로 교체한다. 실패·거부·중단도 같은 블록에 표시하며, 성공 요약만으로 실제 출력을 대신하지 않는다. 결과는 기존 도구·이벤트·뷰포트 크기 한도를 적용하며 비밀값을 제거한다.

```text
  execute_command

    command: go test ./...

    Output
    exit_code: 0
    stderr:
    stdout: ok example/package
```

`!`만 입력하면 전체 명령을 표시하고, 뒤에 글자를 입력할 때마다 일치하는 후보만 남긴다. `!mo`, `!odel`, `!모델`, `!thinking`은 `!model`을 찾는다. 시작 글자가 일치하는 후보를 먼저 표시하며, 검색 결과가 없으면 다른 명령으로 대체하지 않는다. 삭제하면 후보가 다시 넓어진다.

명령 후보는 `Enter` 한 번으로 선택한 명령을 실행하며 `!q`의 `!quit` 선택도 즉시 종료한다. `Tab`은 명령을 입력창에 삽입만 한다. 메뉴·연결 필드·파일 탐색 화면과 이어하기 선택에서도 사용할 수 있다. 종료는 승인을 대신하지 않으며 미승인 Plan과 중단된 작업은 보존한다. worker를 취소·합류하고 모델 연결을 정리한 뒤 터미널을 복원한다. 외부 SIGINT도 동일하게 정상 종료한다.

macOS에서는 터미널이 전달한 `Cmd+C`(Meta+C)도 앱 종료로 처리한다. 기본 복사 단축키로 터미널이 소비하면 앱이 받을 수 없으므로, 해당 터미널에서 `Cmd+C`를 Ctrl+C 바이트(`0x03`) 전달로 매핑해야 한다. 터미널 설정을 자동 변경하지 않는다. `Ctrl+C`는 macOS에서도 지원한다.

`!dir`에서는 탐색 포커스에서도 `:q`를 바로 입력할 수 있다. 하단에 입력 중인 명령이 보이며 `Enter`로 채팅 화면에 복귀한다. `Backspace`로 오타를 수정하고 `Esc`로 명령 입력만 취소한다. 입력 포커스에서도 `:q` + `Enter`를 사용한다. 탐색 포커스의 복귀 명령은 채팅 초안·선택 파일·작업·Plan을 보존하며, 붙여넣기로 실행되지 않는다.

Thinking은 기본 OFF다. 활성화되면 모델명 뒤에 `Thinking`을 표시하고 명시한 강도가 있으면 `Thinking MEDIUM`처럼 함께 표시한다. `!model` 메뉴는 `Thinking ON / OFF` 한 행으로 표시하고 선택값은 굵게, 다른 값은 낮춘 농도로 구분한다. `Thinking effort` 행에서는 모델·Provider에 문서화된 강도만 선택한다. 프로파일의 `DEFAULT`는 강도 필드를 보내지 않는 선택이며, 선택한 강도의 짧은 진단과 저장이 성공한 뒤 적용한다. 같은 모델·주소·프로파일의 세션 선택은 복구하고 모델별 TOML 기본값보다 우선한다. OFF에서는 강도 표시와 요청 필드를 생략하되 선호값은 유지한다. 해당 ON/OFF 행으로 `↑`/`↓` 이동 후 `←`는 ON, `→`는 OFF를 선택하며 `Enter`로 세션·전역 적용 위치를 고른다. 지원하지 않는 제어는 `(unavailable)`로 표시한다. Ollama는 `/api/show`의 boolean·문자열 지원값을 확인하고, vLLM·SGLang은 모델별 프로파일에 기록한 템플릿 제어만 사용한다. 프로파일 대상은 2026년 3월 이후 출시, 전체 300B 이하인 검토된 모델이다. 연결 진단에서 OFF 요청에 reasoning이 반환되면 중단하며, ON/OFF에 동일한 질문을 보내 별도 reasoning의 발생·억제를 확인한 경우만 토글을 활성화한다. 미식별 서빙 별칭은 `~/.v/config.toml`의 주소·Provider·모델별 매핑으로 지정할 수 있다. [모델 목록·프로파일·별칭 설정](model-profiles.md)을 참고한다. 일반 응답과 별도 Thinking 스트림은 구분하여 처리한다. 글자 농도의 실제 표현은 터미널의 bold/dim 지원과 테마에 따른다.

상태줄의 Scope는 `프로젝트` 또는 `전체 시스템`으로 표시한다. 기본 승인 정책은 문구를 생략하고 `allow-all`일 때만 `자동 승인`을 표시한다. 기본 상태줄은 `no-model │ 프로젝트`이며 설정 파일과 정책 값은 그대로 유지한다.

Plan 승인 전에는 변경과 명령 실행을 거부한다. 승인한 revision의 단계를 순서대로 실행하고, `approve` 정책이면 각 실제 변경 제안도 승인받는다. 변경 뒤에는 승인된 검증 명령의 실제 성공 결과를 완료 근거로 요구한다. 읽기만 한 작업은 읽기 검증을 사용할 수 있다. 검증 결과가 입증하는 범위는 실행한 검사에 한정되며, 목표 충족 여부는 별도로 판단한다. 검증을 할 수 없으면 사용자 검토·추가 정보를 요청한다. 승인 거부는 즉시 작업을 중단하고, 실패한 검사는 수정 후 다시 검증할 수 있다. 미승인 Plan과 중단된 Tool Call은 재시작 후 복구하며, 부작용을 자동 재실행하지 않는다. 같은 세션을 두 프로세스에서 동시에 열 수 없다.

파일 생성·수정·삭제의 승인 화면은 줄 단위 unified diff를 표시한다. `-`는 삭제, `+`는 추가, `@@`는 줄 범위이며 변경 주변 3줄만 문맥으로 남긴다. 떨어진 변경 구간은 별도 hunk로 표시하고 PageUp/PageDown으로 탐색한다. 추가 줄은 저채도 짙은 초록색(`#20372C`), 삭제 줄은 저채도 짙은 적갈색(`#422A2D`) 배경과 밝은 회색(`#D8D8D2`) 글자로 화면 끝까지 강조하며, 긴 줄의 감싼 행에도 동일하게 적용한다. 헤더·문맥·승인 메뉴·명령 미리보기는 기본 배경을 유지한다. 마지막 줄바꿈 유무와 CRLF의 `\r`도 표시한다. 비교는 준비된 원본·실제 실행할 고정 내용으로 생성하며 비밀값은 제거한다. 비교 작업 한도(편집 거리 256·비교 작업 1,000,000 또는 65,536 초과 개행)를 넘으면 전체 제거·추가 형태의 확장 diff로 전환해 변경을 생략하지 않는다. 바이너리는 크기·SHA-256으로 표시하고 디렉터리 삭제·이동·명령은 해당 작업 대상으로 확인한다. 승인은 후보 전체에 적용한다.

`directory` Scope에서는 파일 도구와 셸 작업을 프로젝트 루트로 제한한다. 셸은 macOS Seatbelt 또는 Linux 내부 커널 실행기로 격리하며, 외부 파일 접근 실패를 에이전트에게 반환한다. OS·설치된 도구 실행에 필요한 경로는 읽기 전용으로, 실행별 임시 디렉터리는 작업용으로 허용한다. 프로젝트 밖 사용자 파일·다른 프로젝트·V 상태에는 접근하지 못한다. 이 Scope의 셸에서는 네트워크도 허용하지 않는다. 격리가 불가능하면 실행을 거부하며 제한 없는 실행으로 재시도하지 않는다. `system` Scope에서는 기존 OS 사용자 권한으로 실행하며 승인·출력 한도·취소 정리를 적용한다.

셸은 전용 도구로 처리하지 못하는 빌드·테스트 등의 작업에 사용한다. 직접 호출한 `rm`·`rmdir`·`unlink`는 `delete_file`, 파일 읽기·목록·검색·이동·폴더 생성 등은 해당 전용 도구를 사용하도록 오류를 반환한다. POSIX Shell AST로 직접 호출과 알려진 래퍼를 확인하며, 이 분류는 임의 스크립트 내부 동작을 증명하거나 OS 격리를 대신하지 않는다. `approve`는 실제 셸 명령문에 대한 승인을 요구하고 `allow-all`은 개별 승인만 생략한다.

`execute_command`의 모델 입력은 `command` 하나다. 명령별 시간 인자와 기본 120초·최대 600초 제한은 없다. 전체 작업 예산(`[loop].max_seconds`, 기본 4시간)과 사용자 취소는 계속 적용한다. 시간 인자를 없애도 Scope·Permission·Plan 검사는 유지하며, 자동 승인도 Scope를 넓히지 않는다. 다른 도구에는 시간 인자가 없고 `read_file`·`list_directory`의 `offset`·`limit`은 조회 위치와 분량을 정한다.

도구 실행 실패는 `code`·`detail`·`next`와 수집한 출력을 도구 결과로 저장해 다음 모델 문맥에 전달한다. Shell의 비정상 종료에는 표준 출력·오류·종료 코드가 포함된다. 정책 차단·사용자 승인 거절·취소·저장 실패로 작업이 중단되면 다음 모델 호출을 강행하지 않는다.

## 연결 저장·서버 한도·native reasoning

연결 진단과 SQLite 저장이 성공한 뒤 활성 클라이언트를 교체한다. 실패 시 후보를 닫고 기존 연결·설정을 유지한다. API Key는 모델 진단 후 OS 키 저장소의 새 참조에 저장하며, 선택 저장 실패 시 새 키를 정리한다. 기존 대화가 참조하는 키는 보존한다. Thinking 변경도 저장 후 적용한다. 전역 TOML 저장 후 세션 저장이 실패하면 전역값 복원을 시도하고 복원 실패도 알린다.

선택 시 서버 한도를 다시 조회하여 저장하고 `!model → 모델 정보`에 표시한다. vLLM·SGLang은 `max_model_len`, Ollama는 `/api/ps`의 로드된 컨텍스트, LM Studio는 선택 인스턴스의 `config.context_length`를 사용한다. 모델의 이론상 최대 길이를 현재 서버 용량으로 대체하지 않는다. LiteLLM은 같은 별칭의 모든 배포가 값을 제공할 때 입력·출력 한도 각각의 최솟값을 사용한다. 한도를 확인할 수 없으면 미제공 또는 조회 실패 사유를 표시한다.

출력 요청은 확인된 출력·컨텍스트 상한 이내로 제한한다. 준비된 vLLM 모델의 컨텍스트가 알려져 있으면 `/tokenize`에 전체 역할별 메시지와 동일한 템플릿 제어값을 보내 입력 토큰을 계산하고 남은 용량만 출력에 배정한다. 용량이 소진되면 이력을 보존한 채 중단한다. 토큰 사전 계산은 용량 확인에만 사용하고 INPUT/OUTPUT 집계는 실제 생성 usage를 따른다. 다른 Provider의 입력 토큰은 추정하지 않는다. LM Studio에는 `truncation: disabled`를 요청한다. Ollama에는 확인된 현재 컨텍스트를 `num_ctx`로 고정하지만, 공개 Chat API에 입력 사전 토큰 계산·잘림 거부 기능이 없어 서버 내부의 이력 잘림까지 검출·방지할 수는 없다. 컨텍스트 미제공·서버 설정 변경·라우팅 변경도 서버의 최종 검증 대상이다.

Ollama의 문자열 `think` 값은 서버가 광고한 대소문자 그대로 보낸다. LM Studio는 전체 역할별 이력을 전달하는 `/v1/responses`를 사용하며 `store: false`로 원격 대화 저장을 끈다. reasoning 선택지는 native 모델 목록에서 확인한다. 공개 강도는 `reasoning.effort`로 보내고, binary OFF/ON은 `none`/`medium` 후보를 동일 질문으로 대조 진단한 뒤 토글을 제공한다. binary 모델에 강도 목록을 임의로 추가하지 않는다. native `DEFAULT`는 ON을 표현할 수 있는 서버 기본 강도, 없으면 첫 번째 광고 강도를 사용한다. OFF를 제공하지 않는 모델은 검증된 ON을 굵게 표시하고 `OFF unavailable`을 안내하면서 지원 강도는 선택할 수 있다. 짧은 진단은 reasoning 분리와 ON/OFF 동작을 검사하며 각 강도의 내부 연산량까지 측정하지는 않는다. LM Studio의 실제 사용량은 Responses의 `usage.input_tokens`·`output_tokens`에서 읽는다.

## Provider 스트림과 복구

SSE·NDJSON의 누적 전송량·누적 텍스트·단일 프레임 1MiB 제한을 제거했다. 긴 스트림은 프레임을 순차 처리하며 한 프레임 크기에 비례하는 메모리가 필요하다. 비스트리밍 JSON 4MiB, Agent 단계별 응답·인자·요약 및 저장 한도는 각 소유자의 검증 규칙으로 적용한다.

HTTP의 3분 전체 타이머와 모델 호출·연결 진단의 고정 종료 타이머를 제거했다. 모델 생성은 `[loop].max_model_seconds`의 무수신 제한(기본 600초), 메타데이터·연결 진단은 기본 3분의 무수신 제한을 사용한다. 수신 데이터가 있으면 다음 읽기에서 새로 기다리고, 소비자가 데이터를 처리하는 동안에는 네트워크 대기 타이머를 멈춘다. DNS·연결·TLS 초기화 제한과 사용자 취소는 별개다.

네트워크·HTTP·스트림 오류는 기존 연결을 정리하고 **최대 3회 시도(재시도 2회)**한 후 실패 원인을 반환한다. 기본 대기는 250ms·500ms이며 `Retry-After`는 최대 30초까지 반영한다. 메타데이터 재시도는 응답 읽기·JSON 디코딩을 포함한 새 응답 전체를 기준으로 수행한다. 재시도도 Agent의 모델 호출 예산에 포함한다. 사용자 취소, 로컬 요청·Scope·승인·인자·저장 검증 실패와 호출 예산 소진은 즉시 중단한다.

부분 응답에서 재시도하면 응답·Thinking·Compaction 초안을 초기화한 뒤 같은 요청을 다시 생성한다. 이미 실행한 도구를 재실행하지 않는다. 토큰은 각 시도에서 실제 수신한 usage만 기록한다. 출력 한도 등의 종료 오류에서도 이어지는 usage를 수신한 뒤 복구·오류 처리를 진행한다. 최종 오류에는 시도 횟수, HTTP 상태, 제공된 오류 코드·메시지를 표시하며 API Key와 터미널 제어 문자를 제거한다. 선택적 모델 식별 실패는 원인을 `!model → 모델 정보`에 보존하고 일반 연결 진단을 계속한다.

가상 시계로 장시간 수신·무수신 복구·소비자 처리 지연·재시도 대기 취소를 검증했다. 로컬 모의 서버로 8MiB 초과 전송, 4MiB 초과 디코딩, 부분 응답 초기화, 오류 후 usage 수신과 최종 오류 마스킹을 검증했다. 실제 서버·프록시에서 장시간 연결하는 검증은 별도로 필요하다.


## 에이전트 응답의 Markdown

에이전트 답변·진행 설명·스트리밍 응답·복원된 대화에는 제목, 굵게, 기울임, 인라인 코드, 코드 블록, 목록, 인용, 링크, 표를 흑백으로 표시한다. 글자 굵기·밑줄·농도로 구분하며 새 배경색을 사용하지 않는다. 코드 블록의 내용과 공백은 보존하고 구획 표시만 추가한다. 링크는 이름과 주소, 이미지는 대체 텍스트와 주소로 표시하며 외부 리소스를 가져오지 않는다.

물결표는 한국어 범위 표현에 쓰이므로 취소선 확장을 사용하지 않는다. ~문장~와 ~~문장~~, 3~5일 등은 그대로 보인다. 물결표 세 개로 만든 Markdown 코드 블록은 코드 블록 규칙을 따른다.

사용자 입력, 파일 내용, 도구 인자·출력은 Markdown 표시 대상이 아니다. 저장소와 모델 문맥에는 원래 응답을 유지하고 TUI에서만 변환한다. 한글·이모지의 grapheme과 터미널 셀 폭을 기준으로 줄을 나눈다. 256 KiB를 넘는 단일 응답이나 표시 중첩 한도를 넘는 문서는 내용을 자르는 대신 원문으로 표시한다.


## 사용자에게 보이는 줄 번호

read_file의 사용자 화면에는 `7 | 내용`처럼 줄 번호만 표시한다. edit_file 인자의 시작·끝 앵커도 화면에서는 start_line/end_line으로 표시한다. 모델이 사용하는 `7#8자리해시` 앵커, 저장된 도구 호출·결과, 실제 편집 검증은 원문 그대로 유지한다. 이 변환은 실시간 출력과 과거 대화 복원에 동일하게 적용한다. 소스 내용 자체에 포함된 해시나 Git 커밋 ID는 변경하지 않는다.
