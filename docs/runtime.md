# 에이전트 작동 방식

[문서 목록](README.md) · [제품 명세](../SYSTEM.md) · [도구 연동](tools.md) · [실행 경계](execution-boundary.md)

TUI·CLI·서버·WebUI는 같은 모델 요청·도구·승인·저장 흐름을 사용한다. 화면과 전송 방식은 요청 실행의 소유권을 바꾸지 않는다.

## 실행 흐름

1. 사용자 요청, 프로젝트 위치와 지침, 스킬, 저장된 대화를 준비한다.
2. 모델의 답변·Thinking을 스트리밍하고 native 도구 호출을 수집한다.
3. 완성된 호출을 검사하고 필요한 승인을 받는다.
4. 실행 결과와 상태를 저장한 뒤 모델 판단을 이어간다.
5. 남은 실행을 정리하고 최종 답변·사용량·중단 사유를 전달한다.

실제 관측과 모델의 설명은 구분한다. 답변이 끝났다는 사실만으로 테스트 통과나 구현 정확성을 보장하지 않는다.

## 모델 요청 준비

설정한 Provider·모델과 현재 대화를 사용한다. 프로젝트 지침·스킬은 요청에 적용되는 범위로 읽고 원문 이력과 출처를 유지한다. 팀 참여자는 독립 문맥을 가지며 공용 대화만 공유한다.

실행기는 다음 모델 요청의 문맥과 제공할 도구를 준비한다. Provider 어댑터는 이를 연결별 요청으로 변환하고, 실행기는 설정이나 문맥이 바뀐 경우 요청을 다시 준비한다. [모델 연결](model-connections.md) · [도구 등록](tools.md#코어-등록과-실행) · [문맥과 인코딩 재사용](optimization-strategies.md#모델-문맥과-provider)

## 모델 스트림과 복구

Provider의 SSE·NDJSON을 순서대로 해석하며 답변과 Thinking, 완료된 native 호출을 분리한다. heartbeat는 스트림 본문과 별도로 처리한다. Chat Completions는 종료 표식까지 읽으며, `stop`이나 `tool_calls` 프레임 뒤 연결이 정상 종료되면 그때까지 받은 사용량과 함께 확정한다. 도구는 인자와 식별자의 검증을 마친 호출에서 실행한다. [본문 한도](configuration.md#본문-한도) · [종료 판정](../internal/provider/protocol/chunk.go)

본문 없이 native 도구 호출로 응답이 확정되면 이전 텍스트 초안을 정리하되, 해당 응답에서 확정한 Thinking은 표시 정책에 따라 유지한다. 도구 실행으로 넘어가는 순간 추론 표시를 빈 내용으로 덮어쓰지 않는다. [응답 확정](../internal/agent/run/generate.go)

에이전트와 압축의 무수신 예산은 `[loop].max_model_seconds`로 설정한다. 메타데이터 조회와 연결 진단의 기본 무수신 한도는 3분이다. 수신 대기와 소비자 처리 시간은 따로 계산한다. DNS·연결·TLS 초기화 제한과 취소도 개별 경계를 가진다. [실행 예산](configuration.md#자동-승인과-실행-예산)

복구 가능한 전송 오류는 응답 도중에도 최초 요청을 포함해 최대 4회 시도한다. 대기는 1초·3초·5초이며 더 긴 `Retry-After`는 최대 30초 범위에서 우선한다. 각 재시도의 사용량은 따로 기록하고 표시 중인 답변과 Thinking은 유지한다. 다시 받은 앞부분이 일치하면 새 내용만 이어 표시하고, 다르면 검증과 완료를 마친 응답으로 갱신한다. 이미 실행한 도구의 확정 결과를 문맥으로 사용한다. [전송 재시도](../internal/provider/transport/retry.go) · [초안과 재시도](../internal/agent/run/reply_draft.go)

OpenAI·LM Studio Responses에서는 번호가 같은 이벤트를 한 번만 적용한다. 각 항목의 본문·거절·Thinking 조각과 완료 스냅샷을 대조해 빠진 뒷부분을 복원한다. 최종 본문이 스트림과 달라지면 같은 답변을 갱신한다. 확정된 도구 목록과 일치하는 호출만 실행기로 넘긴다. [Responses 완료 처리](../internal/provider/protocol/responses/complete.go)

정상 종료했지만 답변이 비어 있고 완성된 도구 호출도 없는 경우가 있다. Thinking만 받은 경우도 여기에 해당한다. 실행기는 표시 중인 초안을 유지한 채 같은 판단에서 한 번 교정을 요청한다. 형식이 잘못된 도구 호출도 같은 교정 예산을 사용한다. 실제 도구 실행에서 발생한 오류는 그 도구의 결과로 모델에 전달한다. [응답 검증과 복구](../internal/agent/run/loop.go)

완성된 도구 호출의 인자가 스키마와 맞지 않으면 해당 호출에 오류를, 같은 묶음의 나머지 호출에는 실행 보류 사유를 돌려준다. 연속 인자 오류에는 최대 두 번 교정을 요청하고, 계속 실패하면 마지막 오류와 실행 기록을 남긴다. 관찰 원문은 유효한 판단이 저장될 때까지 다음 요청과 대화 복원에서 사용할 수 있다. [인자 교정](../internal/agent/run/tool_reply.go) · [관찰 복원](../internal/storage/sqlite/observation_context.go)

Provider가 출력 토큰 한도를 보고했고 일부 답변이 있으면, 자동 출력 설정에서 도구를 제외한 이어쓰기를 한 번 시도할 수 있다. 원 요청과 이어쓸 요청의 입력 토큰 수를 측정할 수 있고, 후속 요청의 입력과 출력 예산이 창에 들어가야 한다. 현재는 사전 토큰화를 지원하는 vLLM 텍스트 요청에서 이 조건을 확인할 수 있다. 유효한 후속 본문은 기존 답변과 합쳐 한 번 저장한다. Thinking만 남았거나 미완성 도구 호출이 있거나 수동 출력 한도를 설정한 경우에는 받은 부분과 종료 사유를 남긴다. 모든 복구는 현재 작업의 호출·시간 예산을 사용한다. [이어쓰기 조건](../internal/agent/run/text_continuation.go)

## 실행·승인·관측

독립 작업은 병렬로 수행할 수 있지만 같은 대상의 변경과 공유 자원은 실행 경계에서 조율한다. 승인 전에 준비한 후보가 실행 시점에도 유효한지 확인한다. 셸 프로그램 내부의 모든 파일 효과를 추정하지 않는다.

새 사용자 지시는 안전한 판단 경계에서 반영하고 아직 실행하지 않은 후보를 다시 검토한다. 이미 시작한 효과는 결과를 수집한 뒤 다음 판단에 사용한다. 승인 요청·허용 범위는 [호스트 실행과 승인](execution-boundary.md)을 따른다.

## 출력과 저장

답변·Thinking·도구 결과·사용량은 세션 기록에 보존한다. 관련 실행 결과와 체크포인트를 일관되게 확정하고, 저장 실패를 정상 완료로 표시하지 않는다.

화면용 이력·원문 조회·모델 문맥은 서로 다른 투영이다. 완료 통계에는 상태와 검증한 숫자만 전달한다. [사용량 표시](usage.md#화면과-사용량) · [이벤트 계약](diagnostics.md) · [SQLite 저장 전략](optimization-strategies.md#대화-저장과-sqlite)

## 문맥·압축·재개

대화 압축은 다음 판단에 필요한 문맥을 정리하며 원본 DB를 삭제하지 않는다. 최신 요청·실제 도구 결과·호출 관계를 유지하고 실패·취소한 부분과 완료한 결과를 구분한다. 발동 조건과 설정은 [Compaction](configuration.md#프롬프트와-compaction)을 따른다.

진행 중인 실행은 압축 뒤에도 미열람 관찰과 이어 읽기 위치를 유지한다. [관찰의 문맥 수명](tools.md#관찰-결과와-이어-읽기)

저장 대화를 재개하면 해당 프로젝트·선택·기록을 복원한다. 중단된 프로세스에 임의로 재연결하거나 불확실한 파일 효과를 다시 실행하지 않는다. 후속 예약은 화면 수명의 별도 요청이며 중지·실패 때 처리는 [사용 가이드](usage.md#중지와-후속-요청)를 따른다.

## 비대화형 실행

`--print`는 최종 답변, `--mode json`은 순서 있는 이벤트, `--export`는 저장 원문을 제공한다. 대화형 승인을 받을 수 없는 작업은 승인 정책에 따라 중단한다. [비대화형 CLI](cli.md#비대화형-실행)를 따른다.

## 서버 실행

서버는 접수한 작업을 관찰 연결과 독립적으로 실행한다. 접수 키·작업 ID·저장 상태로 중복과 불확실한 결과를 구분한다. 구독 종료는 작업 취소가 아니며 재접속이 작업 재제출로 이어지지 않는다. [서버 API](server.md)를 따른다.
