# Prevent generic output without overriding the product

This original application-oriented analysis reviews Impeccable's craft floor, Operate guidance, refinement workflow and 62-entry detector catalog at the revision below. The catalog contains 31 entries labeled `slop` and 31 labeled `quality`. These are heuristics, not evidence of authorship or a substitute for a useful, working application.

## Distinguish three findings

| Kind | Decision |
| --- | --- |
| Demonstrable defect | Fix broken behavior, missing content, unreadable or occluded text, false state and accessibility failures |
| Pattern warning | Identify its task, content and system reason; revise an unchosen default rather than blindly deleting a familiar pattern |
| Intentional expression | Preserve the requested theme or established identity while checking its actual usability and consistency |

Some upstream prose uses absolute house-style bans. This skill does not make them universal SaaS rules. A familiar font can serve operations, glass can be the requested material and technical values can use monospace. None excuses low contrast, fabricated evidence or missing functionality.

## Apply the analysis throughout

Use this alongside [usability reasoning](usability.md). Let the actual task and content generate the structure; pattern names and detector cues are prompts to investigate, not a closed set of allowed designs. A familiar useful control can be correct, and a new combination can be correct when its benefit, cost and behavior are clear.

| Boundary | Question | Result |
| --- | --- | --- |
| Scenario | What actual task/content justifies a page or region, without invented activity or proof? | Grounded page map with unnecessary template sections omitted |
| Layout | What must be compared or retained, and is it hidden by cards, tabs or disclosure for appearance alone? | Information relationships determine the composition |
| Theme | Does hierarchy/material direct attention and preserve real content, readable type and focus? | Intentional expression with usable roles and fallbacks |
| Implementation | Do feedback, copy, actions and motion express actual state rather than simulate work or success? | Working path with honest pending/failure/recovery |
| Review | Is the issue structural, behavioral or visual, and what evidence supports the correction? | Fix the cause without replacing the brief or inventing quality scores |

For a finding, give location, user effect, evidence and correction. Classify it as a defect, system drift, unchosen pattern or intentional material. A low detector count cannot establish usability, and a warning does not authorize erasing the user's brief.

Use available project checks and visual tools. Do not require the upstream runtime, parallel reviewers or a score database. Never claim a rendered pass without inspecting the result.

## Review the design rather than compliance with an example

Ask which object and decision the hierarchy serves, whether the useful facts can be compared and whether the next action/state is understood. Weak identity may come from uniform composition/type/density rather than insufficient color. A neutral base can retain several deliberate accents; a minimal reader can carry expressive content scale.

Use the target project as the system authority. The studies and upstream house styles cannot turn a specific palette, left rail, frame size, global controller or tool workflow into a general requirement. Review a requested material at its actual role and intensity.

Treat tool findings as scoped evidence. Inspect the real inherited/composited state when a source estimate mixes theme branches or hidden overlays. An actual contrast or focus failure still needs correction; an unexplained warning does not justify arbitrary restyling or invented quality scores.
