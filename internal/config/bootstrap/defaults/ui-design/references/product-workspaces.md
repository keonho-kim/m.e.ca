# Research and authoring studies: transfer the relationship

This level-2 map locates two fictional design studies. They illustrate complete screen relationships with minimal local navigation, tabs, dialogs and inspection. They do not implement a DB/model connection, document editing or export. For a real product derive the behavior and technology from the current request, not these restrictions or sample modules.

Choose a screen for the decision it clarifies. Do not load all eleven, copy a brand reference or turn their page set into a required application plan.

## Sources, question, evidence and conclusion

The research study relates context, structured data, a question, an answer and its actual cited record. It makes scope visible and evidence reachable. Whether source context stays persistently visible, disclosed locally or beside the result depends on how often it is consulted and what must be compared.

| Design question | Study source |
| --- | --- |
| How do project identity and a useful first task meet? | [Workspaces](../assets/examples/databook/workspaces.html) |
| What explains source scope without treating all data as documents? | [Sources](../assets/examples/databook/sources.html) |
| How do object views preserve identity and column meaning? | [Explorer](../assets/examples/databook/explorer.html) |
| Which context should remain beside the answer? | [Conversation](../assets/examples/databook/chat.html) |
| How can a conclusion return to evidence? | [Insights](../assets/examples/databook/insights.html) |

The study uses project modes above answer/evidence and local source disclosure. This saves width at the cost of another step to inspect sources. Persistent sources could be better for a different repeated comparison task. Citations need recognizable emphasis and the correct target regardless of layout.

[App styles](../assets/examples/databook/databook.css) and [citation reveal](../assets/examples/databook/chat.js) show one implementation. The light material and sample account data are case-specific; they do not require a chat-first AI product or one palette for research.

## Brief, structure, authored artifact and review

The office study distinguishes file identity, tools, content navigation, an authored page/slide and relevant assistance. Familiar relationships can support usability without copying another product's branding. Tool chrome stays compact while the artifact receives useful scale.

| Design question | Study source |
| --- | --- |
| Can the library show the work rather than only empty containers? | [Library](../assets/examples/office/library.html) |
| Which input establishes purpose, reader and expected decision? | [Brief](../assets/examples/office/brief.html) |
| How can structure be inspected before detailed authoring? | [Outline](../assets/examples/office/outline.html) |
| When do outline, paper and assistance deserve simultaneous space? | [Document](../assets/examples/office/document.html) |
| How do filmstrip, canvas and notes support another output? | [Slides](../assets/examples/office/slides.html) |
| What helps a person inspect a proposed result before sharing? | [Review](../assets/examples/office/review.html) |

Document and slides are parallel outputs in this case. Their display as choices avoids implying compulsory sequential completion. A real product may use another authoring model. A persistent outline/filmstrip navigates task objects, not global application areas; narrow windows can recompose it without losing the selected content.

Inspect [app composition](../assets/examples/office/office.css), [authoring workspace](../assets/examples/office/office-studio.css) and [outline/filmstrip interaction](../assets/examples/office/office.js). Formatting labels are intentionally static in this shell. They are not evidence that editing, generation or download occurred.

## Read implementation selectively

The studies share [palette-free geometry](../assets/examples/shared/product-shell.css), [type](../assets/examples/shared/base.css), [controls](../assets/examples/shared/components.css), [motion](../assets/examples/shared/motion.css), [native surface lifecycle](../assets/examples/shared/interaction.js), [tab/deep-link behavior](../assets/examples/shared/preview.js), [material fallback](../assets/examples/shared/glass.css), [icons](../assets/examples/shared/icons.svg) and [license](../assets/examples/shared/icons-LICENSE.txt).

Their shared files demonstrate stable mechanics with app-owned expression. Reuse the actual project's framework/components/state mechanism instead of introducing those exact globals or selectors. Preserve identities, drafts, reading position and focus through the chosen representation.
