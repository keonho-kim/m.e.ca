# Turn an uncertain request into a designable task

Use this when the person cannot name the feature or explain what should occupy a screen. Inspect the current product and conversation before asking. A feature inside an established app inherits its context; a bundled example is evidence to study, not a new product brief.

## Resolve the uncertainty that changes the design

| Uncertainty | Useful question | Design consequence |
| --- | --- | --- |
| Outcome | What should become easier for the person using this? | The main task and a recognizable result |
| Usage scene | Who is using it, how often and alongside what work? | Density, visibility, device and explanation |
| Scope | Which existing screen or path should change? | Preserved behavior and the extent of redesign |
| Material | Which actual objects, text, media or data are available? | Content hierarchy and honest gaps |
| Preference | What works in the reference you like? | Transferable proportion, rhythm, interaction or material |

Ask only consequential unresolved questions. Do not require the user to provide a design vocabulary, choose a file or repeat known facts. When a reversible choice is delegated, make a grounded recommendation and name the assumption.

## Translate a vague request into choices

“More professional” may mean clearer reading order, stronger contrast, stable alignment, appropriate density or predictable action/state feedback. Do not assume it means blue, gray, glass or a left rail. “Less flat” may need more typographic contrast, a distinct work surface or clearer region ownership before it needs a shadow. “More color” calls for meaningful accent roles, not an equal rainbow.

Describe the likely cause and propose a fitting change. For an unclear product goal, offer a small number of plausible outcomes with a first screen and a cost. A team losing requests might need a queue, a searchable guide or a stage overview; those alternatives are not a requirement to build all three.

A style reference should answer a design question: what leads, what stays visible, how controls relate to content, or how the interface acknowledges change. Identify that relationship before borrowing its appearance.

## Make a complete, proportional proposal

Describe one path: entry → find/understand → act/create → result → return or recover. Identify the working object and the decisions that depend on it. Then define substantial regions, their content, primary action and applicable missing/failed state.

Mark regions as necessary, conditional or omitted. A dashboard requires an aggregate question; a chat requires conversational work; billing requires an actual commercial task. Keep the useful path small rather than presenting a menu of disconnected SaaS pages.

State whether the requested deliverable is a design, a navigable shell or a functional frontend. Use representative samples for design work. Reuse existing service contracts for functional work and identify unresolved dependencies without inventing endpoints or expanding into unrelated backend development.

## Keep the rationale useful

For a consequential choice use context → difficulty → arrangement → expected benefit/cost → check. For example, a person repeatedly comparing records may benefit from aligned rows and a retained inspector; the cost is less central width. A visual collection may instead put imagery first and move metadata lower, increasing scrolling.

Separate confirmed facts, reversible proposals and unresolved needs. A reference screenshot or attractive prototype establishes neither market demand nor user preference. Use [usability](usability.md) to test the reasoning against the task, not compliance with an asset's layout.
