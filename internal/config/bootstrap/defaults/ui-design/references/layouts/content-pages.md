# Let reading, authoring or inspection lead

A knowledge reader, an authored artifact and a technical console need different central regions. Share useful navigation and control roles while giving the main activity appropriate scale.

## Discovery and reading

An index needs scope, useful discovery, meaningful entry summaries and result states. A reader needs subject identity, readable content, hierarchy and a return/navigation path. Add topic trees, local TOC, versions, related material and access context when they help.

Editorial detail can use a strong title/body contrast, genuine media, captions and deliberate reading rhythm. Serif, cream or a large opening is optional; the relationship between subject, image and text creates the direction. Keep decisive metadata nearby when inspection requires it; moving metadata below a large image increases scrolling.

A local TOC should form a compact group and remain reachable. Sticky placement must follow its content size rather than stretch entries across the article height. At narrow widths choose a useful title/content order, and avoid making navigation consume most of the reading opening.

## Document and presentation work

Separate file identity, tools, object navigation, authored content and relevant assistance. The paper/slide can have more visual scale than the surrounding application title. A document outline and presentation filmstrip navigate the artifact; they are not generic global menus.

Choose editor/preview or assistance panes when concurrent consultation matters. A focused mode with an obvious return may serve better than several narrow panels. Keep output types and editing/review states distinct. Draft saving, publication, scheduled delivery and export are different outcomes when implemented.

## Technical inspection

Keep environment/project/object identity, useful configuration or query input, actual result context and recovery clear. A schema tree can earn width because it expresses real hierarchy. Distinguish global destinations, open objects and result views instead of styling all three as one navigation strip.

Use typography and stable aligned data before decorative instrumentation. Mono belongs to code/identifiers or measurements; explanatory Korean text still needs readable roles. Technical work can be light or dark according to actual use and the brief.

Credentials, history, logs and destructive actions require their real service and access semantics when in scope. A code-styled area is not evidence that an operation ran. Keep sensitive values out of frontend examples and diagnostic output.

## Fit material and feedback

A minimal shell can support editorial reading; compact or frosted tools can surround opaque content. Do not wrap paper inside ornamental cards or use transparency to weaken body text. A metadata list may need a different density than an article.

Render available authored content directly. Use region loading for fetched index/body/configuration and retain valid drafts during save or publication. Show actual phases for imports/builds rather than simulated logs. Use [loading](../loading-and-progress.md), [forms](../components/forms.md) and [navigation](../components/navigation.md) for applicable controls.

Check headings/captions, long mixed-script text, deep links, section anchors, missing media/content and resized/zoomed reading. Verify actual publishing, editing or tool behavior only when part of the deliverable; otherwise keep the shell's limits explicit.
