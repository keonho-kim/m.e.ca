# Compose detail, input and commitment

Use the actual object and outcome to organize the task. Give identity, substantive content, actions, feedback and return a clear relationship. A settings form, record detail and staged commitment can share controls without sharing one page layout.

## Detail: inspect before acting

Make the current object/state, decisive information, supported next action and return context clear. Add history, attachments, related records or section navigation only when useful data supports them.

Decide whether facts must be compared beside the content or can follow an editorial reading sequence. A compact inspector serves repeated inspection; an independent detail gives sustained work more scale. Do not duplicate the whole summary in every tab or fill an empty side region with invented activity.

## Editing: group decisions

Use labeled input groups with relevant requirements, units/help and recoverable errors. A preview or summary belongs when it helps the decision, not because every editor needs three panes. Keep a readable form measure; short related fields may share a row, while dependent or long input needs coherent reading and keyboard order.

Choose consistent section spacing and boundaries across forms that express the same relationship. Give headings more separation from the previous group than from their own fields. Do not inherit layout accidentally from an unrelated page's stylesheet or reset every section to the same generic card.

A long editor can retain commit/cancel actions if they do not obscure final input or errors. Preserve entered work during pending/failure. Distinguish displayed preview, local draft and confirmed persistence in the actual task.

## Stages: use dependencies, not a visual recipe

Choose stages when one decision genuinely constrains the next or a consequential commitment needs review. Keep current stage, content, valid back/continue, retained input and result/return clear. Independent settings may be better as grouped sections.

Changing an earlier dependency can mark later values for review while retaining valid unrelated work. Visiting a stage does not complete it. Document, slides or other parallel outputs may be mode choices rather than sequential steps. Use [steppers](../components/steppers.md) for navigation and [loading/progress](../loading-and-progress.md) for actual execution.

## Settings and first use

Expose account, organization, workspace or device scope. Group values by the person's decisions; state whether changes apply immediately or on commit. Risky operations need a clearly scoped region and proportional review, not red styling throughout an ordinary form.

Authentication, onboarding, plan/billing and administration belong only when the requested product path needs them. A useful empty state can lead to a first result without a long tour. Do not add unavailable settings, commercial facts or personal-data fields to imitate another service.

## Validate the complete path

Known creation labels should appear directly; unresolved fetched values need honest local loading. Submission retains the form and shows feedback near the commitment, rather than skeletonizing input. Use [forms](../components/forms.md) for the selected controls.

Walk inspect → edit → fail → correct → confirm → return where functional behavior exists. Check long Korean labels, IME, dirty close, dependency changes, focus and uncertain outcomes. A design shell can illustrate these arrangements; it must not claim a real save, authorization or transaction from appearance alone.
