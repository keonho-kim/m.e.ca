# Design for comparison, inspection or interpretation

Data presence does not require a dashboard. Choose whether the person is finding/acting on records, repeatedly inspecting objects or interpreting aggregate evidence. That decision determines the leading regions and density.

## Query and results

Keep object/scope context, meaningful conditions, comparable results, applicable continuation and a clear next action. Search, filters, sort and result counts should describe the same applied scope. Edited conditions may differ from the displayed query while work is pending; make that distinction explicit.

Use aligned rows when repeated fields drive comparison. Use cards when imagery or narrative distinguishes independent objects. Keep record identity, decisive values, units and status readable before adding badges or customization. Wide data needs deliberate internal scrolling or field priority, rather than tiny text or clipped content.

A single status filter can narrow one collection; it need not create duplicate tables as separate tab panels. A saved collection and a type/category filter are independent dimensions when the task treats them that way. Do not accidentally reset one scope while changing the other.

Add bulk actions, saved views, export, column controls or an inspector only for real recurring needs. State whether selection covers visible items, explicit IDs or all matching records.

## Master-detail

Retaining a navigable list and selected detail can reduce repeated travel. Keep the selected identity obvious and allocate enough width for both tasks. A no-selection state can be useful; do not invent a record solely to fill an inspector.

An independent route gives long content or editing more room. An editorial detail can lead with media, but moves metadata and may increase scrolling. Keep simultaneous facts visible when the decision requires them. Choose the cost deliberately rather than declaring either layout universally superior.

## Analytical evidence

Begin with a decision and scope/period. Include only summaries that orient it, suitable evidence, definitions and a supported follow-up. Units, denominator, comparison basis, missing/partial/stale values and freshness matter as much as chart type.

A chart earns space when it makes a real relationship easier to understand. An ordered table may answer better. Do not open every analytical screen with four KPI cards or fabricate a trend to make a frame look complete. Unknown is not zero.

## Visual hierarchy

Give query controls, results, local actions and secondary explanation different weights. Use alignment, spacing, type and stable surface roles before extra containers. Accents can distinguish actual selection, categories and status, with labels/marks preserving meaning. A neutral background need not make the work visually uniform.

Let a wider monitor show more useful comparison; cap prose independently. Reserve navigation/inspectors only when their information justifies the width. Contextual actions should be near the affected records without making every cell an action.

## State and inspection

Keep safe headers and meaningful labels during initial region loading. Preserve correctly identified data on refresh; selecting another record must not present the old body as current. Distinguish no data, no matches, denied, failed and retained stale results.

Check representative long names, large amounts, null values, empty queries, late responses, changed selection, continuation and return from detail. Apply [collections](../components/collections.md) for table/list semantics and [loading](../loading-and-progress.md) for feedback. Integration follows the real service contract when functional work is in scope.
