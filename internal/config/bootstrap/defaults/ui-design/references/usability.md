# Derive the interface from use

Choose what people need to read, compare, decide, change and recover. Layouts, controls and effect names are possible answers; they do not define the question. Reuse learned semantics while adapting their arrangement to the actual product.

## Establish the usage scene

| Evidence | Decision it informs |
| --- | --- |
| Goal and working object | Which information leads and what counts as a result |
| Frequency and familiarity | Stable compact operation versus visible explanation |
| Information relationships | Concurrent comparison, sequential reading or optional consultation |
| Risk and reversibility | Prevention, review, confirmation and durable recovery |
| Waiting and uncertainty | What remains usable and what the UI can truthfully claim |
| Interruption and return | Which draft, selection, scope, scroll and context must survive |
| Space and input methods | Pane widths, text scale, keyboard/IME, pointer and zoom behavior |
| Established product behavior | Language, navigation, actual capabilities and trusted conventions |

Use observed context first and label assumptions. Do not invent research or ask the user to design the control. Fewer clicks, more whitespace and fewer visible controls are not universal improvements: hiding a comparison can increase memory burden, while a dense aligned table can reduce repeated travel.

## Turn relationships into composition

State the main task in product terms. Group facts that must be evaluated together. Keep decisive information visible; disclose genuinely occasional detail. Decide which context persists when an object changes and how the person returns.

Choose a credible arrangement and, for consequential uncertainty, compare a simpler alternative. A detail inspector retains a list but consumes width. An editorial detail gives a subject more scale but moves metadata and increases scrolling. A stepper clarifies real dependencies but interrupts independent input. Explain the benefit and cost rather than defending a pattern name.

Global destinations, project modes, task objects, current view and execution stages are different scopes. A schema tree or slide filmstrip can be useful beside a canvas without justifying a global application sidebar. Filtering a collection does not require duplicated peer panels.

## Make expression serve comprehension

Identity comes from information order, proportion, type, density, geometry, imagery, color and motion together. A neutral foundation can carry several purposeful accents; a dark canvas is a use-context decision; a minimal interface still needs hierarchy and discoverable controls.

The content and tools can have different intensity. A compact command area can surround a large authored page. Compact tools can lead to a calm editorial reader. Keep stable action meanings and shared roles while varying the work's composition; do not turn every route into a different brand.

## Apply anti-slop during decisions

Include a region only when actual content and a task justify it. Remove unsupported proof, decorative activity and layout filler. Let emphasis express what matters now. A title names the subject; a status explains a real condition; an action states its consequence.

Investigate repeated cards, generic KPI openings and indiscriminate motion at their cause. Preserve useful familiar patterns and requested expression. A warning about glass, cream or a common font is not a reason to erase a deliberate direction, and intention cannot excuse unreadable text or false state. The [anti-slop map](anti-slop.md) owns that classification.

## Validate the hypothesis

Walk a representative path with real content and applicable failure, keyboard/IME, zoom and interruption. Check whether needed facts can be found and compared, the next action and actual state are clear, and valid context survives. If a choice hides needed information, revise its structure before polishing its effect.

An agent walkthrough is heuristic evidence. Measure time, errors or interaction counts only when actually observed and useful. A screenshot establishes presentation, not a successful save or user preference. Revise the choice when its assumptions change.

Sources informing this synthesis: [GOV.UK design principles](https://www.gov.uk/guidance/government-design-principles) and [usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/). Apply their reasoning to the present context rather than transplanting a service's conventions.
