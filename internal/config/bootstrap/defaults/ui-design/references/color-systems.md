# Eight principles for choosing and distributing color

Derive color from the product, content, operating context and intended material. These are combinable decisions, not eight swatch sets. The bundled studies' role values illustrate choices; they do not form a palette to install in every app.

| Principle | Apply it | Watch for |
| --- | --- | --- |
| Neutral foundation | Establish readable canvas, work surface, ink and boundaries before accents | Monochrome treatment that makes all actions and information equal |
| Functional accent | Give primary action, focus or selection recognizable emphasis with paired ink | Accent repeated on every label, border and background |
| Distributed role-based accents | Use a few stable color families where action, category or meaningful region needs distinction | Random color by card position or an equal-area rainbow |
| Content and brand | Let genuine imagery or established identity guide temperature and emphasis | Sampling every image into changing chrome or treating a logo color as every UI role |
| Semantic status | Distinguish actual success, warning, error, pending and unknown with words/shape as well as color | Green meaning both merely selected and successfully completed |
| Data color | Use sequence for magnitude, divergence around a real midpoint and category for identity | Rainbows for ordered values or changing series identity between views |
| Light/dark relationships | Rebalance luminance, contrast, surface steps and emphasis for the supported scene | Automatic inversion, neon by category or an unnecessary mode toggle |
| Material and inclusive fallback | Evaluate transparency, surface contrast, focus and forced-color behavior on actual backgrounds | Token-only calculations that miss compositing or disappearing shadow-based state |

## Make accents useful across the screen

A neutral minimal base can support several visible accents. Assign meaning first: for example a main action family, stable resource categories and separately reserved real status. Place those cues where they help scanning, choice or recovery. They need not occupy equal areas or appear on every route.

Keep category colors independent from severity. If saved, selected, current and completed use similar treatment, add an explicit label/mark and clarify the role. Do not create badges, statuses or categories merely to spend another hue. A single accent is also valid when fewer distinctions are needed.

Apply a color family through an intentional range: strong foreground/action, paired on-color ink and a supporting tint where useful. Pale fills need adequately strong ink and boundaries. A faint blue wash, desaturated label or disabled-looking button is not professional restraint. Conversely, saturation alone cannot repair weak hierarchy.

## Define roles with real consumers

Use the project's existing tokens for canvas, working/raised/overlay surfaces, primary/supporting ink, separators, interactive boundaries, action/on-action, selection, focus and actual states. Share stable meaning across components without treating every pill or selected surface as the same behavior.

Text, field boundaries and decorative separators have different responsibilities. Preserve readable read-only values and useful disabled explanations; one low-opacity rule cannot serve them all. Use proximity, weight, labels and shape before adding a hue that carries no new information.

Choose light/dark from the request and usage evidence: ambient conditions, sustained reading, data/imagery, adaptation and the incumbent product. Design both only when supported scope calls for both. A dark workbench study is not a rule for all database products; an editorial reader need not be cream or use serif.

## Verify actual pairings

WCAG text contrast normally requires 4.5:1, with 3:1 for qualifying large text. Meaningful non-text control/state cues generally need 3:1 against adjacent colors; not every decorative line or button outline is an essential cue. Apply the actual criteria and exceptions, without rounding a failed value into a pass. See [text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) and [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).

Check on-action, muted, selected, focus, invalid and overlay pairs in every intended material/mode. Glass requires the composited background, controls retain legible state without decorative effects, and charts need labels/legends plus suitable non-color distinctions. Inspect conditional theme inheritance in the real browser when a static estimate is ambiguous.

Record actual checks and their scope. A palette calculation, preview image or automated warning count is not accessibility certification or evidence of user preference.
