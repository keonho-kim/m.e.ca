# Compose substantial regions before unit controls

A layout expresses information relationships. Start with the working object, what must be read together, the action and return path. Then choose regions and controls. The vocabulary is open-ended; combine, vary or omit it according to the task.

| Need | Focused blueprint | Question to resolve |
| --- | --- | --- |
| Product identity and repeated navigation | [Application shell](layouts/app-shell.md) | Which destinations and context deserve persistent space? |
| Search, records and analytical evidence | [Data workspaces](layouts/data-workspaces.md) | What must be compared at once? |
| Independent detail, input and commitment | [Task flows](layouts/task-flows.md) | What is sequential, editable or consequential? |
| Queues, collaboration and AI work | [Collaboration](layouts/collaboration.md) | What context and result representation support the next action? |

| Discovery, transaction and time/resource work | [Commerce and booking](layouts/commerce-and-booking.md) | Which facts establish a valid choice and confirmed result? |
| Explanation and activation | [Public pages](layouts/public-pages.md) | What must a visitor understand before acting? |

## A region has an observable job

Specify the question it answers, real content/scope, supported action, relationship to its neighbors and relevant missing-data behavior. A box titled “Analytics” without a meaningful question is not an analytical region. A large title without a subject is not a hero.

Necessary roles may merge. An object header can hold identity, state and an action. A summary can retain the few facts needed while editing. Add an inspector, toolbar or activity region only when it reduces a real cost; each consumes width and attention.

## Choose an arrangement from the relationship

| Arrangement | Useful relationship | Main cost |
| --- | --- | --- |
| Split/master-detail | Frequent inspection with retained collection context | Less width for the central work |
| Reading/detail destination | Sustained independent content or editing | More travel back to comparison |
| Board/timeline/calendar | State or chronology is the decision axis | Harder comparison of unrelated fields |
| Visual collection | Appearance and narrative distinguish objects | Less efficient dense-field comparison |
| Weighted/asymmetric grid | Importance or media proportions differ | Reading order and alignment need deliberate control |
| Focused canvas | Spatial position and direct manipulation carry meaning | Orientation, scale and alternative controls become necessary |
| Sticky context/action | Repeated return to essential controls | Occlusion and nested scrolling risk |

A large screen can reveal more objects, more detail or concurrent context; choose which benefit matters. Cap prose independently from wide data. Above-the-fold is an observation at a particular viewport, not a fixed pixel rule or a demand to fit every field into one screenshot.

## Separate navigation scopes

Global areas, project modes, object trees/outlines/filmstrips, local views and workflow stages are different relationships. Keep their labels and current state legible. A genuine content tree can remain beside the work even when the global destinations are above it. A shallow service does not need an empty permanent rail.

## Establish hierarchy before material

Use proportion, content scale, type, alignment, meaningful insets and density to show what leads. Flatness can come from uniform emphasis rather than insufficient shadows. Surface treatment or color cannot repair missing information architecture. Choose material after the region roles, allowing a calm working surface beside more expressive content.

Inspect useful minima, long labels, viewport height, zoom and focus. Recompose secondary panes before shrinking text. Keep scroll ownership explicit and leave the last row, field, popup and action reachable. Test the selected path, not only a full-state opening.
